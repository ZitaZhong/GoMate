# DD-17 实时深度研究（联网深搜 + 证据护栏 + 实时入库）· 详细设计

**详细设计系列 · v2 新增能力 · v1.0 · 2026 年 7 月**

> 本文定义 v2 的头号新能力：**实时深度研究（Deep Research）**——当用户用自然语言表达需求（或系统检测到数据缺口/过期）时，**实时联网**对目的地当周活动与出行信息做多源深度检索，产出**带证据、可追溯官方、可入库复用**的结构化结果，并**流式**回传进度。
>
> **上游依据**：v2 增补 D3/D4/D5/D6；`周末去哪儿_技术架构与实现方案_v1.md`（§5.3 活动情报、原则一"当周即研"、原则四"证据优先"）；`02_开源技术分析`（GPT-Researcher 的 Plan-and-Solve + Source-track）；DD-03（证据护栏，**不可动**）、DD-04（web 深搜/LLM Provider）、DD-06（抽取/归一/定级/去重/入库管线，复用）、DD-05（入库后复检召回）。
> **下游消费者**：DD-15 对话 Copilot（触发并展示进度）、DD-02 `deep_research` 节点、DD-05 检索（融合实时结果）。
> **一句话**：**实时找到最新的、且能回溯到官方来源的信息——把"实时"与"可信"同时拿到，绝不退化为编造。**

## 1. 模块职责与边界

| 项 | 说明 |
|---|---|
| **职责** | **每次需求强制全量**实时联网深度研究，采用**有界迭代研究环**（借鉴 LangChain Open Deep Research 三段式 + Supervisor/并行子研究 + CRAG/Self-RAG 反思-纠正）：澄清成 brief → 迭代研究（搜索/阅读/抽取/反思补缺，受 R_max 与时间预算约束）→ 官方核实 → 定级 → 实时入库 → 复检 → 流式进度。 |
| **边界内** | 触发判定、研究规划（问题拆解）、多源搜索编排、官方来源核实策略、并发/超时/缓存/配额治理、流式进度事件、`deep_research` 节点/服务、深研缓存与作业表。 |
| **边界外** | 抓取/清洗/抽取/归一/去重/定级/入库的**底层实现**（复用 DD-06 管线，本模块只以"同步入口"驱动它）；证据定级规则（DD-03）；检索召回（DD-05）；web 搜索 Provider 底座（DD-04）。 |
| **架构位置** | v2 数据流"深路径"；挂在 DD-02 图上作为 `deep_research` 子图/节点，由 DD-15 Copilot 触发。 |

## 2. 设计目标与非目标

**目标**：① **实时最新**——分钟级拿到当周新增/临时活动与出行提示；② **可追溯官方**——每条事实带来源与六态，核心事实回官方核实；③ **可复用**——结果入 `activities` 库；④ **可感知**——全程流式进度；⑤ **有界迭代**——像业界 Deep Research（OpenAI/Gemini/LangChain Open Deep Research）那样"搜索→反思→识别缺口→再搜"多轮迭代，但**有界**（R_max + 时间预算，见 §5b），不做无界长跑。

**非目标**：❌ 不产生无源事实；❌ 不碰交通实时票价/余票（DD-03 闸三不变）；❌ 纯闲聊/纯问已生成信息（`chitchat`/`ask_info`）不触发深搜；❌ 不做刷票/代购；❌ **不做无界长跑**——周末场景要求分钟级有界收敛（预算上限 300s，见 §5b；区别于通用 DR 的 10+ 分钟）。

## 3. 深搜策略（每次需求强制全量实时深搜）

**产品决策（v2 拍板）**：深研由 `.env` 总开关 `DEEP_RESEARCH_ENABLED` 控制（默认开）；**开启时，每次规划需求都强制执行全量实时联网深搜**（跑 §4 的有界迭代研究环），不做"库够就跳过"的门控——保证用户拿到的永远是"此刻最新"的信息。关闭时退化为快路径（仅读预热库）。

| 项 | 说明 |
|---|---|
| **默认行为** | 每次首规划 + 每次涉及"去哪/活动/最新"的细化轮，**都跑全量深搜**（不因库覆盖/新鲜度而跳过） |
| **库的角色** | 预热库（DD-06）不再是"门控（够就不搜）"，而是**即时垫场**：先秒级返回库结果占位，深搜结果流式补充/覆盖 |
| **不跳过** | 移除 `should_deep_research` 的"库足够→跳过"分支；相关轮深搜恒执行 |

```python
def needs_deep_research(turn, cfg) -> bool:
    # 总开关(.env DEEP_RESEARCH_ENABLED)：关 → 退快路径(仅库)；开 → 强制全量。
    if not cfg.DEEP_RESEARCH_ENABLED:
        return False
    # 强制全量：凡涉及目的地/活动/出行信息的需求，一律跑有界迭代深研（不看库覆盖）。
    return turn.intent in ("provide_constraints", "refine_field",
                           "deep_research", "clarify_answer")
    # 仅纯 ask_info / chitchat / confirm_booking 不触发（无新数据需求）
```

> **性能兜底（不削减覆盖，只约束延迟）**：为让"强制全量"可用，保留 ①**流式**——先垫库结果 + 深搜进度实时推；②**并发上限 + 整体超时 → `partial`**——到点返回已核实部分，绝不无限等；③**极短防抖缓存**——同一 query 数分钟内的重复/并发调用复用（避免同一需求重复打全网），**可关闭**。以上均**不跳过深搜**，只保证体验与成本可控。
>
> **代价须知（已知并接受）**：强制全量深搜显著增加**延迟（秒级 → 十几秒）**与**搜索/LLM 成本**；通过流式垫场 + 超时 `partial` + 防抖缓存 + 并发/配额上限缓解（§9）。

## 4. 深度研究流程（有界迭代研究环 —— 三段式，接地气对齐业界）

> **业界对齐**：借鉴 **LangChain Open Deep Research**（三段式 Scope→Research→Write、Supervisor 委派并行子研究、反思识别缺口再补研究）与 **CRAG/Self-RAG**（评估检索质量→不足则纠正/再检索）；并叠加我们的**官方核实 + 证据六态 + 交通禁编**护栏。与通用 DR 的差异：我们**产结构化活动入库**（非写报告），且**有界**（R_max + 时间预算）。

```text
【Scope 定范围】(复用 DD-15 多轮澄清)
   把对话澄清压成 research brief(北极星): 城市×本周末×品类 + 具体活动 + 出行提示
   │
【Research 有界迭代研究环】Supervisor + 并行 Sub-agents
   ┌────────────────────────────────────────────┐
   │ Supervisor 按 brief 拆子主题(品类/城/具体活动) → 派并行 Sub-agents │
   │ 每个 Sub-agent = 工具调用循环: search(DD-04) → 抓取/清洗(DD-06)  │
   │   → 抽取(emit_activity+evidence_quote) → 清洗 findings 回传        │
   │ ★Supervisor 反思-补缺(每轮, 受 R_max):                          │
   │    评估 findings 对 brief 的【覆盖度+置信度+冲突】              │
   │    来源分级(CRAG式): 官方场馆/文旅/主办方 > 开放数据 > 社区(仅线索)│
   │    识别 gap(品类未覆盖/日期缺失/多源冲突/只有搜索源未回官方)   │
   │    → 生成 follow-up 子任务 → 再派 Sub-agent → 再评估              │
   │ 停止(任一): 覆盖≥阈值 且 核心活动官方确认 且 无未解冲突           │
   │           | 达 R_max | 超时间预算 → 返回 partial                    │
   └─────────────────────────────────────────────┘
   │
【Synthesize 收敛入库】(我们不写报告，产结构化活动)
   归一/去重(pgvector) → enforce_provenance 定级(DD-03)
   → ingest_realtime 入库(DD-06) + embed(DD-05) → DD-05 复检召回融合
   → 未解 gap 明确标注(unknown + 官方源清单)
   │
【全程流式】每轮进度回 DD-15: "第2轮: 发现音乐节信息缺口，正在补搜官方票务…"(§6)
```

**上下文工程（来自 Open Deep Research 教训）**：① 对话压成 brief 防 token 膨胀；② Sub-agent 先清洗 findings 再回 Supervisor（深研 token 用量可达普通对话 ~15×，必须裁剪）；③ 多智能体**仅用于并行研究**，收敛入库单次完成（并行"写"易失协调）。

**与通用 Deep Research 的关键差异（更严格、更聚焦）**：① 产出是**结构化活动记录 + 证据六态**，不是散文报告；② **官方核实优先**（不"取高频"——旅行事实高频≠正确，只有官方才算已确认）；③ **交通票价/余票禁编**（DD-03 闸三）；④ **有界**（R_max/预算），适配周末场景的秒级~分钟级预期。

## 5. 数据模型（新增，需回改 DD-01）

```sql
-- 深研作业（可观测/幂等/复用；DD-01 待并入）
CREATE TABLE deep_research_jobs (
  id          BIGSERIAL PRIMARY KEY,
  plan_id     BIGINT REFERENCES plans(id) ON DELETE CASCADE,
  trigger     TEXT NOT NULL,          -- user_explicit/coverage_gap/stale/long_tail_city
  query       JSONB NOT NULL,         -- {city, weekend, categories, nl}
  status      TEXT DEFAULT 'running', -- running/succeeded/partial/failed/timeout
  found_activity_ids BIGINT[],        -- 入库的 activities.id
  source_count INT DEFAULT 0, official_count INT DEFAULT 0,
  started_at  TIMESTAMPTZ DEFAULT now(), finished_at TIMESTAMPTZ,
  error       TEXT
);
-- 深研缓存（相同查询短期复用，控成本）
CREATE TABLE deep_research_cache (
  query_hash  TEXT PRIMARY KEY,       -- sha1(city+weekend+categories 归一)
  result_ids  BIGINT[], source_list JSONB,
  created_at  TIMESTAMPTZ DEFAULT now(), expires_at TIMESTAMPTZ  -- 当周数据短 TTL(如 6h)
);
```

> 深研**结果**本身落 `activities`（复用 DD-06 表，带 evidence）；本表只存**作业与缓存元数据**。

## 5b. 配置（`.env` 环境变量，项目可自定义）

深研的开关、迭代轮数、时间预算等**全部走 `.env`**（`pydantic-settings` 读取，DD-17/DD-04/DD-02 共用）：

```bash
# —— 深度研究开关与预算（可按项目/环境自定义）——
DEEP_RESEARCH_ENABLED=true          # 总开关：false=退快路径(仅读预热库)，不联网深搜
DEEP_RESEARCH_MAX_ROUNDS=3          # R_max：Supervisor 反思-补缺迭代轮上限
DEEP_RESEARCH_TIME_BUDGET_S=300     # 单次深研总时间预算(秒)，到点返回 partial
DEEP_RESEARCH_MAX_SUBAGENTS=4       # 每轮并行 Sub-agent 上限
DEEP_RESEARCH_CONCURRENCY=8         # 搜索/抓取并发上限
DEEP_RESEARCH_CACHE_TTL_S=300       # 极短防抖缓存 TTL(秒)；设 0 关闭(每次全新联网)
DEEP_RESEARCH_MIN_COVERAGE=0.8      # 充分性阈值：覆盖度达标才提前收敛
DEEP_RESEARCH_SEARCH_PROVIDER=bocha # 搜索源：bocha|tavily|exa|serper (见 DD-04)
```

```python
# wheretogo/config.py（pydantic-settings）
class DeepResearchSettings(BaseSettings):
    DEEP_RESEARCH_ENABLED: bool = True
    DEEP_RESEARCH_MAX_ROUNDS: int = 3
    DEEP_RESEARCH_TIME_BUDGET_S: int = 300
    DEEP_RESEARCH_MAX_SUBAGENTS: int = 4
    DEEP_RESEARCH_CONCURRENCY: int = 8
    DEEP_RESEARCH_CACHE_TTL_S: int = 300
    DEEP_RESEARCH_MIN_COVERAGE: float = 0.8
    DEEP_RESEARCH_SEARCH_PROVIDER: str = "bocha"
```

> 这样"深度 vs 延迟/成本"的平衡可由项目**改 `.env` 即调**，无需改代码。默认：开、3 轮、300s、覆盖 0.8、搜索源 bocha。300s 是预算上限（到点返回 `partial`），非典型耗时；等待期间有 SSE 进度心跳（实现：`research/supervisor.py` 每 ~15s 发一次等待进度事件），用户不空等。

## 8. 护栏（DD-03，不可动 —— 本模块的生命线）

- 每条深搜结果**必带 `evidence`**（source_type/source_url/fetched_at/verification_status）；
- **官方核实才 `official_source_confirmed`**；仅搜索命中未核实 → `public_source_observed`；无出处 → `unknown`；**绝不 `confirmed`**；
- **交通票价/余票**：深搜**不产**这些字段（`train.*`/`flight.*`/`*.availability` 由 DD-10 回填或官方，DD-03 闸三 CI 断言兜底）；
- 内容社区（小红书等）**仅作线索**，不作唯一证据；
- 前端展示：深搜结果同样经 `FactField` 六态渲染（DD-13），未核实项明确标"公开来源·待确认"。

> **一句话**：深搜让"新鲜"进来，护栏保证"新鲜"不等于"编造"。

## 9. 成本 / 延迟治理与降级

| 手段 | 说明 |
|---|---|
| **全量深搜** | 每次相关需求**强制执行**（§3）；库结果仅作即时垫场，不作跳过门控 |
| **缓存** | `deep_research_cache` 相同查询短 TTL 复用（当周 6h） |
| **迭代有界** | Supervisor 反思迭代 ≤ `DEEP_RESEARCH_MAX_ROUNDS`；覆盖达 `DEEP_RESEARCH_MIN_COVERAGE` 提前收敛 |
| **并发+超时** | 并发 ≤ `DEEP_RESEARCH_CONCURRENCY`；总预算 `DEEP_RESEARCH_TIME_BUDGET_S` 到点返回**已核实部分 + 官方源清单** |
| **配额** | web 搜索/LLM 走 DD-04 令牌桶 + 日成本上限 |
| **流式** | 首个进度事件秒级返回，用户不空等 |
| **降级链** | 搜索挂→输出关键词+官方源清单（v1 韧性）；抽取失败→入 `activity_review_queue` 人工复核；超时→`partial` + 已得结果 |

## 10. 效果与验收标准（DoD）

1. **实时最新**：对"本周末新增/临时活动"，深搜能在超时内返回并入库（对照人工核对的当周清单，命中率达标）。
2. **可追溯官方**：深搜结果 `official_source_confirmed` 占比达标；每条可点开 `source_url`。
3. **不编造（红线）**：构造"搜到的疑似车次/票价" → 断言其被降级为 `unknown`、且交通字段不入 bundle（CI，与 DD-03 闸三联测）。
4. **强制全量**：每次相关需求都执行深搜（库充足也搜）；仅纯 `ask_info`/`chitchat` 不触发（用例覆盖）。
5. **流式**：首个 `research_progress` 事件 p95 < 2s；整体超时有 `partial` 兜底。
6. **可复用**：深搜入库后，下次同查询走快路径命中（缓存/库命中验证）。

## 11. 开发任务拆解

1. `should_deep_research` 触发判定 + 快/深路径接线（1d）
2. 研究规划（问题拆解）+ 多源搜索编排（DD-04）（1.5d）
3. 来源分级 + 官方核实策略（1.5d）
4. 复用 DD-06 抽取/归一/定级/去重 + `ingest_realtime` 同步入口（1.5d）
5. 流式进度事件 + DD-15 对接（1d）
6. 缓存/并发/超时/配额治理（1d）
7. 护栏联测（DD-03 闸三）+ 效果验收（golden 当周清单）（1.5d）

## 12. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 深搜延迟高伤体验 | 触发式 + 快路径优先 + 流式进度 + 超时 partial |
| 成本失控 | 缓存 + 配额上限 + 并发限制 + 触发条件收敛 |
| 幻觉/编造（最致命） | DD-03 三闸不动 + 官方核实定级 + 交通字段禁编 + 抽取带 evidence_quote |
| 抓取合规 | 复用 DD-06 robots/限速/只公开页 |
| 官方源难核实的活动 | 降级 `public_source_observed`/`unknown` + 标"待确认"，不冒充已确认 |
