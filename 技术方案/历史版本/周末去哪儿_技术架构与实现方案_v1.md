## 1. 现有技术方案调研与竞品洞察

### 1.1 市场上的三类玩家

| 类别 | 代表 | 技术形态 | 与本产品的关系 |
|---|---|---|---|
| **OTA 内嵌 AI 助手** | 飞猪「问一问」、携程「问道」、马蜂窝「AI 小蚂」、支付宝出行助手 | 多智能体 + 自有库存实时数据（机票/酒店价、用户位置），生成可下单方案 | 强，但**不中立**：推荐服务于自家库存与佣金；决策与交易绑定 |
| **通用 Chatbot / 搜索** | 豆包、DeepSeek、Kimi、夸克、秘塔 | 通用大模型 + 联网搜索 | **爱编造**：航班/车次/票价/营业时间常被幻觉，"第一批 AI 旅游受害者"已出现 |
| **垂类行程规划工具** | Mindtrip、Wanderlog、Roam Around、圆周旅行、Wanderboat | LLM + POI 库 + 地图，偏"生成攻略/行程表" | 偏静态攻略，弱在**跨城交通门到门决策**与**多人协同**，且面向境外场景居多 |

**行业公开评测信号**：2025 年发布的《AI 旅行助手评价体系》中，飞猪「问一问」以 724.92/900 居首，其能力核心是"实时数据 + 多智能体协作 + 商品卡片联动"。这说明**"实时可信数据 + 编排"已被验证为价值点**，但头部产品都绑定交易，中立决策层仍是空位。

### 1.2 关键洞察（决定架构走向）

- **洞察一：中立性是结构性护城河，不是口号。** 头部都是 OTA，推荐必然向库存倾斜。本产品"搜索/决策层 → 官方交易平台 → 行程整合层"的三明治结构，天然回避佣金冲突——**代价是拿不到实时库存，必须用"策略卡 + 深链 + 回填"替代"直接下单"**。这不是妥协，而是刻意的可信边界。
- **洞察二：幻觉是垂类 AI 旅游的头号事故源。** 通用 chatbot 编造车次票价导致用户踩坑。本产品必须把"**不许 AI 编造交通/票价/余票/营业时间**"做成**架构级强约束**（第 7 节 Provenance Guard），而不是提示词里的一句请求。
- **洞察三：真正的技术难点不在"生成漂亮行程"，而在三件脏活：**
  1. **当周活动的可信采集与结构化**（无全国统一 API，见 2.3）；
  2. **门到门交通决策**（确定性计算，不靠模型感觉）；
  3. **长周期、可中断、可回退的两段式编排**（用户离开去 12306 买票，几小时/几天后回来继续）。
  这三件事，才是投入产出比最高的工程投资。
- **洞察四：LangGraph 1.0（2025-10 GA）让"可持久化状态机 + 人在环"从自研变成选型。** 产品要的"每步状态可见、可回退、等待交通确认"恰好是它的原生能力（见 3.1）。

## 2. 数据与 API 来源可行性矩阵（核心）

> 这是全案**可行性的地基**。每一格都标注：能力、真实限制、合规、成本、我们的用法、降级策略。
> 结论先行：**火车票、活动、餐饮三类"没有开放实时 API"，正是产品"不做交易 + 用户回填 + 证据优先"设计的现实根因。**

### 2.1 交通 —— 火车 / 高铁（12306）

| 维度 | 事实 |
|---|---|
| 官方 API | **不存在。** 12306 从未对外开放分销或查询 API，并多次公开声明"从未授权任何第三方平台发售火车票"。 |
| 第三方"API" | 均为**爬虫封装或代购**，稳定性差、随时失效、且违反 12306 规则与个人信息合规要求，**不可作为核心基础设施**。 |
| 预售规则 | 预售期 **15 天（含当天）**；各车站起售时间不同；12306 官方提供**起售提醒、预填、候补**（每人 6 个候补订单，每单可选 3 个乘车日期，累计 ≤60 车次）。 |
| **我们的用法** | ①**查询策略卡**（该查什么、为什么）；②**官方入口深链 + 预填清单**；③基于官方 15 天规则**计算起售时间并提醒**（标注"以 12306 当前页面为准"）；④**回填**（文本/截图/手输）。**绝不抓取余票、绝不代购。** |
| 降级 | 抓不到任何数据也不影响：策略卡与起售时间是**规则计算**，不依赖实时接口。 |

> **这是本产品最反直觉、也最正确的取舍**：正因为 12306 封闭，"不做交易 + 回填"不是退而求其次，而是唯一合规且稳定的路径。

### 2.2 交通 —— 飞机

| 维度 | 事实 |
|---|---|
| 航班时刻/动态 | **可付费获取**。飞常准（VariFlight）国内航班覆盖率 99.99%，提供航班动态、时刻、机型、甚至票价；已上线 MCP Server。聚合数据（juhe.cn）等亦提供航班动态查询接口。 |
| 机票比价/实时价 | 可通过 VariFlight 付费获取近似价，但**实时可售价与库存仍应回到航司/OTA**。本产品**不做比价爬取**。 |
| **我们的用法** | ①用 VariFlight/聚合数据取**航班时刻 + 机型 + 准点率**，做**门到门**与"该查哪些时段/机场"的策略；②**比价入口交给用户信任的渠道**（航司官网 / OTA / Google Flights / Skyscanner）；③**回填**确认实际航班。 |
| 成本 | 航班数据为**商用付费**，按调用量/包月计费，需缓存 + 配额治理（第 11 节）。 |
| 降级 | 无航班数据时，退化为"机场对比清单 + 时段建议 + 用户自查"，仍可用。 |

### 2.3 当周活动（产品最核心的数据资产）

| 维度 | 事实 |
|---|---|
| 全国统一 API | **不存在。** 文旅部有信息中心/公共文化发展中心与"AI+文旅"倡议，但**无干净的全国开放活动 API**；大麦网早年开放平台已基本不可用，现存"大麦 API"多为**爬虫封装**，法律与稳定性风险高。 |
| 现实来源（按可信度分级，与 PRD 一致） | ①主办方/场馆/博物馆/剧院/体育馆**官网**；②城市文旅局与**公共文化日历**；③开放活动数据接口（部分城市/平台适用时）；④**搜索发现**（仅用于找入口，事实回官方核实）；⑤**用户提供的活动链接**；⑥人工精选；⑦内容社区仅作灵感线索。 |
| **我们的用法** | 自建**活动情报流水线**（第 8 节）：来源注册表 → 低频克制抓取 → LLM 抽取结构化 → 归一/去重/实体对齐 → 证据库 → 过期清理 → 人工审核台。**每条活动都是一条带证据的记录**，`verification_status` 决定它能否作为"核心活动"。 |
| 合规 | 只采集**明确允许访问的官方公开信息**，遵守 robots.txt 与站点规则，低频、克制、带 UA 与联系方式。 |
| 降级 | 搜索/抓取全挂：输出**搜索关键词 + 官方来源清单**，请用户粘贴链接继续（PRD 韧性表）。 |

### 2.4 地图 / 地理编码 / 路线 / 距离矩阵 —— 高德开放平台

| 维度 | 事实 |
|---|---|
| 能力 | Web 服务 API 覆盖：**地理/逆地理编码、POI 搜索 2.0（关键字/周边/多边形/ID）、步行/驾车/公交/骑行路线规划、距离测量、坐标转换、行政区查询**。 |
| 配额/计费 | 有**免费日配额**（如地理编码个人日配额较高，QPS 有上限），超出**按量计费**；企业实名可提额。**必须做响应缓存 + 配额治理**。 |
| **我们的用法** | ①地址解析、POI 搜索（餐厅/场馆）；②"机场→酒店→展览→晚餐→车站"逐段接驳的路线与耗时；③探索阶段用**粗略直线距离/距离矩阵**控成本，城市确定后再算**精确路线**。 |
| 备选 | 百度地图 / 腾讯位置服务能力相当，可作为**多供应商降级**（抽象为统一 `MapProvider` 接口）。 |
| 降级 | 额度受限：启用缓存 + 生成"一键直达地图链接"（PRD 韧性表）。 |

### 2.5 天气 —— 和风天气（QWeather）

| 维度 | 事实 |
|---|---|
| 能力 | 实况、30 天预报、**逐小时预报**、**分钟级降水**、**灾害预警**、AQI、生活指数；全球数据。 |
| 计费 | 提供**免费开发订阅**（有频次限制），2025-03 起下调价格；标准/高级订阅按量。个人开发者认证即可申请 Key。 |
| **我们的用法** | 天气作为**概率信号直接参与排程**：降水概率高→室外降权/增室内备选；高温→减少长距离步行；强对流/预警→不推荐高风险户外。**触发点**：方案生成时、行前 72h、行前 24h、用户手动刷新。 |
| 备选 | 彩云天气（分钟级降水强项）可作为降水专项补充。 |

### 2.6 餐饮 / POI

| 维度 | 事实 |
|---|---|
| 大众点评/美团 | 开放 API **仅面向商户/合作方**（到餐/酒店 API 需 token/sign/aesKey 商务合作），**普通开发者拿不到**；爬取有合规风险。 |
| **我们的用法** | **以高德 POI 为主**（餐厅坐标、营业时间、电话、类别、评分字段），服务于**行程动线**上的饭点安排；**用户可 BYO 链接**（把点评/小红书收藏的店粘进来），系统做位置对齐与路线计算。 |
| 降级 | POI 不足时，退化为"推荐餐饮区域 + 用户自选 + 一个稳妥备选"。 |

### 2.7 大模型（LLM）与信息抽取

| 维度 | 事实 |
|---|---|
| 可选模型 | 通义千问 Qwen（阿里云百炼）、DeepSeek、智谱 GLM 等，均支持 **Function Calling + 结构化/JSON 输出**；2026 年价格战使调用成本极低。 |
| 抽取/OCR | **Qwen-OCR / Qwen-VL-OCR** 专为票据/表格/文档文字与结构化抽取设计，适合"截图回填"（火车票/机票/酒店确认页）。 |
| **我们的用法** | **小模型做抽取**（回填、活动字段抽取，高频低价）；**大模型做复杂调研与解释**（偏好冲突分析、方案取舍解释）；**支持用户自带 Key（BYO Key）**，数据主权在用户手里；**敏感位置/订单字段脱敏后**才进模型。 |
| 搜索 | LLM 联网检索用**博查（Bocha）/ Tavily / Serper** 等搜索 API（仅用于找官方入口，事实回官方核实）。 |

### 2.8 一句话总结这张矩阵

> **能确定性算的（地图、天气、时间、预算、门到门）→ 交给确定性服务和付费 API；
> 会变、会售罄、会绑账户的（火车票、航班实时价、活动余票）→ 交给官方平台 + 用户回填；
> 需要理解与解释的（自然语言、抽取、取舍）→ 交给分层 LLM，且套上防幻觉护栏。**
> 这条分界线，就是整套架构的设计主轴。

## 3. 技术选型对比与决策

### 3.1 编排引擎：LangGraph（决策）

产品要求："显式状态机驱动，每步状态可见、可回退；等待交通确认后再生成最终计划"。这是一个**长周期、可中断、需持久化、含人在环**的工作流。

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **LangGraph 1.0** | 可持久化状态机；`interrupt()` 原生人在环；Checkpointer 落 Postgres，跨天恢复；流式；被 Uber/LinkedIn/摩根大通采用 | 生态偏 Python（有 JS 版但略滞后） | ✅ **首选** |
| Temporal | 工业级持久化工作流、重试/补偿强 | 偏后端任务编排，LLM/人在环需自研胶水；学习曲线陡；对"每步对用户可见"支持弱 | 备选（超大规模再引入） |
| Dify / Coze 等低代码 | 上手快 | 黑盒、难以表达"证据状态/可回退"复杂逻辑、锁定平台 | ❌ 不适合作为核心 |
| 自研状态机 | 完全可控 | 重复造轮子；持久化/恢复/HITL 都要自己扛 | ❌ 不划算 |

**决策：核心规划流程用 LangGraph（Python），Checkpointer 用 Postgres。** 两段式的"等待用户回填"就是一次 `interrupt`，天然匹配。

### 3.2 语言 / 运行时（决策）

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **TS 前端 + Python 规划服务**（推荐） | LangGraph/爬虫/OCR/OR-Tools 生态在 Python 最成熟；前端用 Next.js 体验最佳 | 双语言、两套部署 | ✅ **推荐** |
| TS 全栈（Next.js + LangGraph.js） | 单语言、共享类型、Vercel 友好 | LangGraph.js 略滞后；数据/抓取/求解生态弱 | 团队极小、想省运维时可选 |

**决策：** 采用 **Next.js(TS) 前端/BFF + 单一 Python 服务（规划编排 + 情报流水线 + 抽取）**。两个可部署单元，兼顾"轻后端"与"数据脏活需要 Python 生态"。

### 3.3 前端形态：Next.js PWA（决策）

- **移动端优先 Web/PWA**（PRD 明确形态）。Next.js（App Router）+ Serwist/next-pwa 做离线与安装；Tailwind + shadcn/ui 快速搭 UI；TanStack Query 管服务端状态。
- **Web Push（VAPID）** 做提醒；**ICS 动态订阅**做零依赖日历。
- PWA 而非原生 App 的理由：跨平台一份代码、无需应用商店审核、与"深链跳官方平台"的开放连接理念一致。

### 3.4 存储（决策）

| 用途 | 选型 | 理由 |
|---|---|---|
| 主库 | **PostgreSQL** | 关系 + JSONB（活动/证据半结构化）+ 事务 |
| 地理 | **PostGIS** | 城市/POI/区域空间查询 |
| 去重/语义 | **pgvector** | 活动实体对齐与去重（同一活动多来源） |
| 缓存/限流/队列 | **Redis** | 地图/LLM 响应缓存、API 配额令牌桶、轻量任务 |
| 异步任务 | **Celery（Redis/RabbitMQ）** | 抓取、抽取、提醒调度 |
| 对象存储 | **OSS/S3** | 回填截图（可设短生命周期，隐私） |

**一个 Postgres 打三份工**（关系 + PostGIS + pgvector），契合"轻后端"。

### 3.5 抓取与网页抽取（决策）

- **静态页**：`httpx` + `selectolax/BeautifulSoup`；**JS 重渲染页**：Playwright（无头）。
- **LLM 友好正文抽取**：Jina Reader / Firecrawl 或自建 Readability，把页面转干净 Markdown 再喂 LLM，降低 token 与噪声。
- **合规优先**：遵守 robots.txt、低频、缓存、带可识别 UA 与联系邮箱；只抓官方公开页。

### 3.6 排程求解（决策）

- 周末行程规模小（2 天、少量活动），**用确定性启发式调度器 + 可行性校验器**即可（贪心排点 + 缓冲 + 硬约束检查），可解释、可回退。
- **多人公平性优化**（v0.2+）再按需引入 **OR-Tools CP-SAT** 做小规模约束优化。**不一上来就上重型求解器**。

### 4.2 两条数据流（一读一写）

- **规划请求流（同步，秒级）**：用户约束 → BFF → Planner 状态机逐节点执行，读**领域服务 + 已就绪的活动库**，流式吐出城市卡/策略卡/计划卡。**此流不做实时抓取**（慢且不稳），只消费**预热好的数据 + 确定性计算**。（⚠️ v2 已调整：见顶部提示——快路径读预热库垫场 + 深路径每次强制全量实时深搜）
- **情报生产流（异步，持续）**：Celery 定时任务按来源注册表低频抓取 → 抽取 → 归一去重 → 写证据库。**把“慢而脏”的采集与“快而准”的规划解耦**——这是保证规划响应速度与可信度的关键设计。

### 4.3 统一外部 Provider 抽象

所有外部依赖（地图/天气/航班/搜索/LLM）都封装为统一接口，内建 **缓存 → 限流 → 重试 → 熔断 → 降级** 五件套：

```python
class Provider(Protocol):
    name: str
    async def call(self, req: Req) -> Result: ...

class ResilientProvider:
    """缓存优先 + 令牌桶限流 + 熔断 + 降级到备用 Provider/规则兜底"""
    def __init__(self, primary, fallbacks, cache, limiter, breaker): ...
    async def call(self, req):
        if hit := await self.cache.get(req.key): return hit
        if not self.limiter.allow(): return await self._fallback(req)   # 配额保护
        if self.breaker.is_open(): return await self._fallback(req)     # 熔断
        try:
            r = await self.primary.call(req)
            await self.cache.set(req.key, r, ttl=req.ttl)
            return r
        except Exception:
            self.breaker.record_failure()
            return await self._fallback(req)  # 降级：备用供应商 → 规则兜底 → 明确 unknown
```

> 这一层把 PRD「韧性设计」表格的每一行都落到代码：任何单点失效都不至于让用户拿到空结果，最差也返回“标注为 unknown + 官方入口”。

```text
[10] PlanComposer          确认版 Trip Bundle
  │
  ▼
[R] Replan 触发器          天气变化 / 信息变更 / 行前检查 / 手动刷新
                           → 回到相应节点局部重算（不推翻已确认项）
```

**为什么这个结构可落地：**

- 第一阶段（1→4）**只依赖已就绪数据 + 确定性计算**，几秒内出探索版，不卡在实时抓取上；
- `interrupt()` 让“等待用户去 12306/航司买票”成为**一等公民**：状态落 Postgres，用户几天后回来继续，不丢上下文；
- 回填后（5→10）才生成**确认版**，兑现“交通未确认前不给伪精确日程”的承诺；
- Replan 只在**有意义的时刻**触发，不打扰用户。

### 5.2 状态定义与图构建（LangGraph）

```python
from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command

class TripPlanState(TypedDict):
    plan_id: str
    stage: Literal["explore", "await_booking", "confirm"]
    constraints: dict            # 聚合后的匿名约束：出发地/时间窗/预算区间/偏好/禁忌
    party: list[dict]            # 每位同行人的脱敏约束（仅聚合展示，不外泄个体）
    candidate_cities: list[dict] # 城市卡（含 evidence 与 status）
    activities: list[dict]       # 候选活动（来自证据库，带 verification_status）
    transport_options: dict      # 门到门比较 + 策略卡 + 深链
    bookings: list[dict]         # 用户已回填并确认的车次/航班/酒店
    hotel_area: dict
    local_routes: list[dict]
    dining: list[dict]
    timeline: list[dict]
    validation: dict             # 硬约束校验结果
    bundle: dict                 # 最终 Trip Bundle（探索版/确认版）
    warnings: list[str]

def build_graph(checkpointer):
    g = StateGraph(TripPlanState)
    g.add_node("parse", constraint_parser)          # LLM
    g.add_node("discover", destination_discovery)   # 确定性 + 活动库
    g.add_node("research", activity_research)
    g.add_node("transport", transport_strategy)     # 确定性门到门
    g.add_node("await_booking", await_booking_node) # interrupt
    g.add_node("hotel", hotel_area_planning)
    g.add_node("mobility", local_mobility)
    g.add_node("dining", dining_planning)
    g.add_node("timeline", timeline_solver)
    g.add_node("validate", feasibility_validator)
    g.add_node("compose", plan_composer)

    g.add_edge(START, "parse")
    for a, b in [("parse","discover"),("discover","research"),("research","transport"),
                 ("transport","await_booking"),("await_booking","hotel"),
                 ("hotel","mobility"),("mobility","dining"),("dining","timeline"),
                 ("timeline","validate"),("validate","compose")]:
        g.add_edge(a, b)
    g.add_edge("compose", END)
    return g.compile(checkpointer=checkpointer)

def await_booking_node(state: TripPlanState):
    # 第一阶段结束：先产出探索版 bundle，再中断等待回填
    explore_bundle = compose_explore_bundle(state)
    user_bookings = interrupt({           # 持久化并把控制权交回用户
        "type": "await_booking",
        "explore_bundle": explore_bundle,
        "prefill": build_prefill_hints(state["transport_options"]),
    })
    return {"bookings": user_bookings, "stage": "confirm"}
```

**恢复执行**：用户回填并确认后，BFF 调用

```python
graph.invoke(Command(resume=confirmed_bookings),
             config={"configurable": {"thread_id": plan_id}})
```

LangGraph 从 Postgres 检查点恢复，无需重跑前四步。**“可回退”**通过 checkpoint 历史 + `update_state` 回到任一节点重算实现，天然支持产品的“每步可见、可回退”。

## 6. 数据模型与证据体系

### 6.1 证据是一等公民

PRD 的六种信息状态是**产品可信度的核心 KPI**（“未确认字段被错误展示为已确认的次数——必须为 0”）。所以证据不是附加字段，而是**每个事实值的包装类型**：

```python
from enum import Enum
from datetime import datetime
from pydantic import BaseModel, HttpUrl

class VerificationStatus(str, Enum):
    confirmed_by_user = "confirmed_by_user"
    official_source_confirmed = "official_source_confirmed"
    public_source_observed = "public_source_observed"
    estimated = "estimated"
    unknown = "unknown"
    expired = "expired"

class SourceType(str, Enum):
    official_venue = "official_venue"; culture_bureau = "culture_bureau"
    open_dataset = "open_dataset"; search = "search"
    user_provided = "user_provided"; editorial = "editorial"; community = "community"

class Evidence(BaseModel):
    source_type: SourceType
    source_url: HttpUrl | None = None
    fetched_at: datetime | None = None
    verification_status: VerificationStatus
    confidence: float = 0.0          # 0~1，用于排序与展示强弱
    note: str | None = None

class Fact(BaseModel):
    """任何对用户展示的事实值都用 Fact 包装：值 + 证据。"""
    value: object | None
    evidence: Evidence
```

**前端渲染铁律**：`estimated`/`unknown` 与 `confirmed` 永远长得不一样（不同底色/角标）。UI 组件直接读 `evidence.verification_status` 决定样式，**杜绝把估算值伪装成已确认值**。

### 6.4 多人聚合的隐私模型

- 每位同伴通过**匿名邀请令牌**填自己的出发地/时间/预算区间/偏好；
- 系统只持久化**聚合结果**（如“最晚返回 = 各人最小值”“预算 = 区间交集/分布”），个体精确预算与家庭地址**默认不入库、不外显**；
- `PartyConstraint` 只存**脱敏粒度**（商圈级而非门牌），用于门到门估算；
- 分享卡默认隐藏：精确家庭地址、个人预算上限、证件信息、私人备注。

## 7. AI 使用策略与防幻觉护栏

### 7.1 分层模型分工（省钱又可控）

| 任务 | 模型档位 | 选型示例 | 频次/成本特征 |
|---|---|---|---|
| 约束解析、追问 | 中档通用 | qwen-plus / DeepSeek-V3 | 单次会话若干次，量小 |
| 活动字段抽取 | 小模型 | qwen-turbo / qwen-flash | 高频、批量、要便宜 |
| 截图/票据回填 | 多模态 OCR | Qwen-OCR / Qwen-VL-OCR | 中频、按图计费 |
| 复杂调研、偏好冲突、取舍解释 | 高档 | qwen-max / DeepSeek-R1 / GLM-4.5 | 低频、要质量 |
| 联网找入口 | 搜索 API + 抽取小模型 | 博查/Tavily + qwen-turbo | 只找入口，不做事实源 |

**路由原则**：能用规则/确定性服务解决的，绝不调模型；必须调模型的，先小后大；用户自带 Key（BYO Key）时，走用户配额，数据主权归用户。

### 7.2 脱敏与数据主权

- 进模型前，**精确位置（门牌）降级为商圈级**、**订单证件号/联系方式打码**、**个人预算脱敏为区间**；
- 脱敏在 BFF 与 Planner 边界处强制执行（一个 `redact()` 中间件），模型侧永远看不到原始 PII；
- 支持用户填自己的模型 Key（阿里云百炼/DeepSeek/OpenAI 兼容端点），请求直连用户配额，服务端不落 Key 明文（KMS 加密或仅会话内存）。

### 7.3 Provenance Guard —— 把“不许编造”做成代码

这是整个产品可信度的**技术命门**。PRD 明确列出 LLM **不允许自行编造**：航班、车次、票价、余票、活动时间、营业时间、实时空位。落地方式不是提示词请求，而是**三道硬闸**：

**闸门一：字段级来源白名单。** 每个字段声明“允许的来源类型”，违反即拒绝写入。

```python
# 只有这些来源能给对应字段“确认级”状态；LLM 输出一律降级为 estimated/unknown
FIELD_SOURCE_POLICY = {
    "train.departure_time": {"user", "official"},   # 车次时间只能来自用户回填或官方
    "train.price":         {"user", "official"},
    "flight.number":       {"user", "official", "variflight"},
    "activity.start_at":   {"official", "open_dataset", "user"},
    "restaurant.open_hours": {"amap", "official", "user"},
    # ... LLM 不在任何交通/票价字段的白名单里
}

def enforce_provenance(field: str, value, source_type: str) -> Fact:
    allowed = FIELD_SOURCE_POLICY.get(field, set())
    if source_type in allowed:
        return Fact(value=value, evidence=Evidence(
            source_type=source_type, verification_status=map_status(source_type)))
    # 来源不在白名单：值可保留为“线索”，但状态强制降级
    return Fact(value=value, evidence=Evidence(
        source_type=source_type, verification_status=VerificationStatus.estimated,
        note="来源不足以确认，需用户/官方核实"))
```

**闸门二：结构化输出 + Schema 校验。** LLM 只能通过 Function Calling 返回**带来源的结构化对象**；缺 `source_url`/`fetched_at` 的“事实”直接判为 `unknown`。

**闸门三：交通/票价/余票的“禁止生成”规则。** 在 `PlanComposer` 出稿前跑一遍断言：任何 `train.*`/`flight.*`/`*.availability` 字段若 `source_type == 'llm'`，直接抛错并替换为“待你在官方平台确认”。**这条断言进 CI 单测**——对应 PRD 的硬 KPI“未确认字段被错误展示为已确认 = 0”。

```python
        "evidence_quote": {"type": "string", "description": "支撑上述字段的页面原文片段"}
      },
      "required": ["title", "evidence_quote"]
    }
  }
}
# evidence_quote 强制模型“指出出处”，抽取结果可回溯校验，杜绝空口生成
```

### 7.5 提示词纪律

所有面向事实的 Prompt 统一遵守：**“不知道就说不知道；给结论必须能指到来源；禁止把估算写成确定。”** 这不是礼貌用语，而是与 Provenance Guard 配套的第一层防线。

## 8. 活动情报流水线

> PRD 称之为“最值得长期建设的资产”。它就是 4.2 里的**异步情报生产流**，与规划请求彻底解耦。

### 8.1 流水线阶段

```text
来源注册表(Source Registry)
   │  调度器按 fetch_interval 低频触发
   ▼
抓取(Fetcher: httpx/Playwright)  ── 遵守 robots、限速、缓存 ETag/Last-Modified
   ▼
正文清洗(Readability/Jina → Markdown)
   ▼
抽取(LLM emit_activity + evidence_quote)
   ▼
归一(Normalizer: 时间/城市/场馆/坐标 via 高德地理编码)
   ▼
去重&实体对齐(fingerprint 规则 + pgvector 语义近邻)
   ▼
证据库(activity 表, verification_status 定级)
   ▼
过期清理(expires_at 到期下架) + 人工审核台(编辑复核/纠错/加白)
```

### 8.2 来源注册表（可运营、可扩展）

```sql
CREATE TABLE source_registry (
  id             BIGSERIAL PRIMARY KEY,
  name           TEXT NOT NULL,              -- 如“中国国家博物馆-展览”
  city_code      TEXT,
  source_type    TEXT NOT NULL,              -- official_venue/culture_bureau/open_dataset
  entry_url      TEXT NOT NULL,
  parser_kind    TEXT,                       -- static/js/rss/api
  fetch_interval TEXT DEFAULT '1 day',       -- 低频克制
  robots_ok      BOOLEAN DEFAULT TRUE,       -- 抓前核对 robots
  trust_level    INT DEFAULT 3,              -- 1~7 对应 PRD 的可信度分级
  enabled        BOOLEAN DEFAULT TRUE,
  last_fetched_at TIMESTAMPTZ
);
```

> v0.1 只需为 15~20 个城市各注册“若干高价值官方源”（博物馆/大剧院/美术馆/体育馆/文旅局日历）。**这是运营活，不是算法活**——正是产品护城河的正确投入方向。

### 8.3 合规红线（写进代码，不靠自觉）

- Fetcher 启动前**强制校验 robots.txt**；对无明确许可的站点默认**不抓**；
- 全局与单域名**双层限速**（令牌桶），夜间调度，带真实 UA + 联系邮箱；
- 只取**公开活动信息**，不碰登录后内容、不碰个人数据；
- 尊重缓存头（ETag/Last-Modified），无变化不重复抓；
- 内容社区（小红书等）**仅作灵感线索**，绝不作为唯一证据源。

### 8.4 去重与实体对齐

- **一级去重（规则）**：`fingerprint = hash(标准化标题 + 城市 + 场馆 + 开始日期)`；
- **二级对齐（语义）**：对 `title+venue` 生成 embedding，pgvector 余弦近邻 > 阈值判为同一活动的不同来源，**合并证据、保留最高可信来源为主记录**；
- 多来源冲突时，**可信度高的官方源覆盖搜索源**，并记录冲突以便人工审核。

### 8.5 verification_status 定级规则

| 命中来源 | 定级 | 能否作为“核心活动”推荐 |
|---|---|---|
| 官方场馆/主办方页 | `official_source_confirmed` | ✅ 可 |
| 文旅局/公共文化日历 | `official_source_confirmed` | ✅ 可 |
| 开放数据接口 | `public_source_observed` | ⚠️ 可，标注需确认 |
| 仅搜索发现、未回官方核实 | `public_source_observed` / `unknown` | ❌ 不作为唯一核心活动 |
| 已过 `expires_at` | `expired` | ❌ 自动下架 |

> 对应 PRD：“活动余票未知→明确标注，且不作为唯一核心活动”。**定级直接决定它在推荐里的权重与展示样式。**

## 9. 关键功能的落地实现要点（含代码）

### 9.1 门到门交通比较（确定性核心，不靠模型感觉）

这是产品护城河之一：**不比“飞行 2 小时 vs 高铁 4.5 小时”，而比完整门到门成本**。全部是可解释的确定性计算：

```python
from dataclasses import dataclass

@dataclass
class Leg:
    minutes: int          # 耗时
    source: str           # amap / rule / user / variflight

def door_to_door(origin, dest_city, mode, depart_window) -> dict:
    """返回门到门总耗时 + 有效游玩时间，每段都带来源。"""
    if mode == "rail":
        to_hub   = amap_route(origin, nearest_station(origin))        # 到发车站
        buffer   = Leg(25, "rule")                                    # 进站/安检缓冲
        run      = rail_runtime(origin.city, dest_city, depart_window) # 时刻表(静态/回填)
        egress   = Leg(15, "rule")                                    # 出站
        to_first = amap_route(dest_station(dest_city), dest_city.core) # 到首个活动/酒店
    elif mode == "air":
        to_hub   = amap_route(origin, nearest_airport(origin))
        buffer   = Leg(90, "rule")                                    # 值机/安检/登机缓冲
        run      = flight_runtime(origin.city, dest_city, depart_window) # VariFlight 时刻
        egress   = Leg(35, "rule")                                    # 下机/取行李
        to_first = amap_route(dest_airport(dest_city), dest_city.core)
    total = sum(l.minutes for l in [to_hub, buffer, run, egress, to_first])
    effective_play = compute_effective_play_time(depart_window, total)  # 有效游玩时间
    return {"total_minutes": total, "legs": [...], "effective_play": effective_play,
            "evidence": collect_leg_sources([to_hub, run, ...])}
```

- 缓冲时长（安检/值机/出站）用**可配置规则常量**，标为 `estimated`；
- 探索阶段用**高德距离矩阵/直线距离**粗估控成本；城市确定后才算精确路线；
- 输出三类默认方案：**时间优先 / 稳妥优先 / 均衡**（对应 PRD 交通比较卡）。

### 9.4 住宿区域决策（先区域后酒店）

```python
def recommend_lodging_area(city: CityPlaybook, activities, return_hub) -> list[dict]:

    for area in city.lodging_areas:                 # 城市档案预置的候选区域
        t_act = avg(amap_eta(area.center, a.location) for a in activities)
```

### 9.5 时间线求解器 + 可行性校验

周末只有 2 天、活动数量少，用**确定性贪心排点 + 硬约束校验**即可，可解释、可回退（不上重型求解器）：

```python
def solve_timeline(bookings, activities, dining, city) -> list[Slot]:
    slots = []
    cursor = arrival_time(bookings)                 # 从到达时刻开始
    for act in order_by_open_and_priority(activities):
        leg = amap_route(cursor.place, act.location) # 接驳
        cursor = advance(cursor, leg.minutes)
        slot = place_activity(act, cursor)           # 尊重开放时间/时长
        insert_meal_if_due(slots, dining, cursor)    # 到饭点就在动线上插餐
        slots.append(slot); cursor = slot.end
    append_return_buffer(slots, bookings.return_leg) # 返程缓冲
    return slots

def validate(slots, constraints) -> Validation:
    issues = []
    if overlaps(slots): issues.append("HARD_CONFLICT")            # 硬冲突
    if not meets_return_buffer(slots): issues.append("RETURN_TIGHT")
    if violates_open_hours(slots): issues.append("CLOSED")
    if over_budget(slots, constraints.budget): issues.append("OVER_BUDGET")
    return Validation(ok=not any(is_hard(i) for i in issues), issues=issues)
```

- **日程硬冲突率**是 PRD 的质量 KPI：`validate()` 的 `HARD_CONFLICT` 计数直接进埋点；
- 校验不通过 → 回到 `TimelineSolver` 或 `TransportStrategy` 重排，或给出“放宽哪个约束”的建议（对应 PRD 无票策略）。

## 10. 韧性与降级设计

把 PRD「韧性设计」表的每一行落到具体机制：

| 场景 | 工程机制（已在前文定义） |
|---|---|
| 搜索服务不可用 | Provider 熔断 → 输出搜索关键词 + 官方来源清单，引导用户粘链接（§4.3 / §2.3 降级） |
| 官方页面结构变化 | 抽取失败→降级为展示链接，请用户确认时间/价格；异常入人工审核台（§8） |
| 地图额度受限 | 命中缓存优先 + 令牌桶限流；超额时生成“一键直达地图链接”代替实时计算（§4.3） |
| 交通未确认 | 状态机停在 `interrupt`，只出时间窗与策略，**不生成伪精确日程**（§5.1） |
| 活动余票未知 | `availability_status=user_must_confirm`，且不作为唯一核心活动（§8.5） |
| 酒店未定 | 输出住宿区域卡 + 筛选条件，而非具体酒店（§9.4） |
| AI 服务异常 | 规则模板兜底：用城市档案 + 确定性服务生成简化计划（不依赖 LLM） |
| 跨城方案均不成立 | `DestinationDiscovery` 回退至近郊/同城候选（降半径重算） |

**总原则**：任何单点失效，用户仍拿到一份有用输出（最差 = “unknown + 官方入口”）。降级不是异常分支，而是每个 Provider 的默认能力。

### 11.1 部署拓扑（MVP 极简，可平滑扩展）

```text
MVP（单机/小集群，docker-compose 即可）：

  • Planner (FastAPI+LangGraph) → 1 容器
  • Worker (Celery: 抓取/抽取/提醒) → 1 容器
  • PostgreSQL(+PostGIS+pgvector) → 托管 RDS 或自建
  • Redis → 托管或自建
  • OSS/S3 → 截图存储（短生命周期）

扩展：Planner / Worker 无状态（状态在 Postgres checkpoint），水平扩容即可。
```

### 11.2 成本结构（MVP 量级的量化思路）

| 项 | 计费模式 | 控成手段 |
|---|---|---|
| LLM | 按 token（小模型极便宜） | 分层路由 + 结果缓存 + BYO Key 分流 |
| 高德地图 | 免费日配额 + 超额按量 | 缓存（地理编码/路线重用）+ 探索阶段用粗估 |
| 和风天气 | 免费开发订阅 + 按量 | 城市级缓存 + 只在触发点拉 |
| VariFlight 航班 | 商用包月/按量 | 时刻数据缓存（变化慢），比价交用户 |
| 搜索 API | 按次 | 仅找入口，低频 |
| 服务器/存储 | 固定 | MVP 单机足够 |

> **“轻后端”的成本实质**：真正持续花钱的不是服务器，而是**外部 API 调用 + 情报运营**。因此“缓存 + 配额治理 + 读写解耦”不是优化项，是刚需。

### 11.3 配额治理

- 每个 Provider 一个**令牌桶 + 日成本上限**；接近上限自动降级（换备用源/规则兜底/提示稍后）；
- 缓存分层 TTL：地理编码高缓存、路线中等、天气短、活动库由流水线预热；
- 埋点每日各 Provider 调用量与命中率，持续优化缓存命中。

## 12. 安全、合规与隐私

- **不碰交易**：不代登录、不代购、不读支付与密码——从架构上消除最大合规风险；
- **数据最小化 + 脱敏**：精确地址/个人预算/证件不入库或脱敏存（§6.4 / §7.2）；截图短生命周期，用完即删；
- **PIPL 合规**：邀请链接匿名、聚合展示不泄露个体；用户数据可导出/可删除；明确授权后才保存个人上下文；
- **采集合规**：只抓官方公开页、遵 robots、低频、带标识 UA（§8.3）；不建立面向交易平台的抓取依赖；
- **BYO Key 安全**：用户模型 Key 不落明文（KMS/会话内存）；
- **传输与鉴权**：全程 HTTPS；邀请令牌最小权限、可过期；关键接口限流。

## 结语

这套方案的每一个技术选择，都回到同一条主轴：

> **能确定性计算的交给服务与付费 API；会变、会售罄、会绑账户的交给官方平台 + 用户回填；需要理解与解释的交给分层 LLM，并套上防幻觉护栏。**

它不依赖任何“拿不到的 API”：12306 无需拓票，活动无需全国统一接口，餐饮无需点评开放。所有“拿不到”的地方，恰恰是产品“不做交易 + 回填 + 证据优先”设计的现实根因。因此它现在就能开工，且每一块都站得住可行性的拷问。
