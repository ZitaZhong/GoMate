## 增补 A（P0）检索质量：把「VECTOR(1024)」变成「推得准」

### A.1 为什么这是最该补的一处

v1 里 pgvector 只用于**去重**（§8.4），但"给用户推哪些城市/活动/餐厅"的**检索质量**没有规格化。而竞品被反复点名的头号毛病，恰恰是检索质量：

- 飞猪问一问："3 个方案只是瘦西湖/东关街/何园…热门景点的**排列组合**"（观察者网实测）；
- 携程问道："泛化能力稍欠，**找餐馆还不那么妥帖**"（北二外副院长邓宁）。

**检索质量 = 产品是否"半吊子"的分水岭。** 我们有一个结构性优势——推荐是**当周活动驱动**（新鲜事件库），天生不是"静态热门 POI 排列组合"；但要把这个优势兑现，必须补上"**召回 → 重排**"两阶段管线，否则再好的活动库也推不准。

### A.2 两阶段检索管线（召回 → 重排）

```text
用户约束(城市 / 周末时间窗 / 预算 / 偏好 / 忌讳)
   │
   ▼ 【召回 Recall】混合检索：一条 SQL 打三重条件
   ├─ 硬过滤: 城市 + 周末时间窗 + verification_status + ST_DWithin(地理)
   ├─ 稠密:  BGE-M3 向量 <=> 查询向量        (语义 / 近义 / 主题)
   └─ 稀疏:  BM25 / pg_search on 标题+场馆     (专有名词 / 精确词 / 罕见实体)
        └─ RRF 融合 → top-100 候选
   │
   ▼ 【重排 Rerank】BGE-reranker-v2-m3 交叉编码
        以"约束 + 偏好"为 query，对 top-100 精排 → top-K
   │
   ▼ 喂给 DestinationDiscovery 打分 / ActivityResearch / DiningPlanning
```

> 为什么两阶段：稠密向量擅长语义但对**专有名词/场馆名/罕见活动**召回弱，BM25 正相反，二者互补（RRF 融合）；重排（cross-encoder）是 RAG 里**性价比最高的一环**，把"召回够但排序糙"修正为"最相关的排最前"。

### A.3 embedding 与重排选型（来自《向量库调研》）

| 用途 | 首选 | 备选 | 理由 |
|---|---|---|---|
| embedding | **BGE-M3**（1024 维，dense+sparse+ColBERT 一体，自托管） | Qwen3-Embedding（0.6B/4B/8B，支持 MRL 降维，效果上限更高） | 一个模型同时产 dense+sparse，未来上混合检索**零额外成本** |
| 重排 | **BGE-reranker-v2-m3**（中文强、轻量、自托管） | Cohere Rerank 3.5（托管、多语种） | 召回 top-100 → 重排 → top-10，中文场景性价比最高 |

**一致性铁律**：入库与查询必须**同模型、同维度**；换模型必须**全量重嵌** → 因此新增 `embedding_version` 字段（见 A.4）。

### A.4 DDL 补丁（对 v1 §6.3 的 `activity` 表）

```sql
ALTER TABLE activity
  ADD COLUMN embedding_version TEXT DEFAULT 'bge-m3-v1',    -- 换模型时用于筛选全量重嵌
  ADD COLUMN search_tsv tsvector                             -- BM25 / 全文检索
    GENERATED ALWAYS AS (
      to_tsvector('simple', coalesce(title,'') || ' ' || coalesce(venue,''))
    ) STORED;

CREATE INDEX ON activity USING GIN (search_tsv);                       -- 稀疏检索
CREATE INDEX ON activity USING hnsw (embedding vector_cosine_ops);     -- 稠密检索(百万级)
-- 规模到千万级：切 pgvectorscale 的 StreamingDiskANN + SBQ（内存可控、召回高）
```

> 中文分词：`simple` 够起步；要更好的中文召回，可换 `zhparser`/`pg_jieba`，或直接用 `pg_search` 的 BM25 扩展。

### A.5 召回 SQL（一条完成 地理 + 结构化 + 语义 —— pgvector 的杀手锏）

```sql
-- 稠密召回（带硬过滤，单事务内完成）
SELECT id, title, verification_status, embedding <=> :q_vec AS dist
FROM activity
WHERE city_code = :city
  AND start_at BETWEEN :wk_start AND :wk_end
  AND verification_status IN ('official_source_confirmed','public_source_observed')
  AND expires_at > now()
  AND ST_DWithin(location, :center, :radius_m)     -- geography 类型按米过滤
ORDER BY embedding <=> :q_vec
LIMIT 100;

-- 稀疏召回（同样硬过滤 + BM25）
SELECT id, ts_rank(search_tsv, plainto_tsquery('simple', :q_text)) AS bm25
FROM activity
WHERE city_code = :city AND start_at BETWEEN :wk_start AND :wk_end
  AND expires_at > now() AND search_tsv @@ plainto_tsquery('simple', :q_text)
ORDER BY bm25 DESC
LIMIT 100;
```

> 这正是《向量库调研》强调的、专用向量库难以企及的组合：**地理 + 结构化 + 语义三重条件，单条 SQL、单个事务完成**，无需跨系统同步或回 JOIN。这也是"pgvector 装在 Postgres 里"这个 v1 决策的最大红利。

### A.6 RRF 融合 + 重排（应用层）

```python
from collections import defaultdict

def rrf(rank_lists: list[list[str]], k: int = 60) -> list[str]:
    """倒数排名融合：只依赖排名、无需分数归一化，业界最常用、最鲁棒。"""
    scores = defaultdict(float)
    for ranks in rank_lists:
        for pos, doc_id in enumerate(ranks):
            scores[doc_id] += 1.0 / (k + pos)
    return sorted(scores, key=scores.get, reverse=True)

def retrieve_activities(city, weekend, constraints) -> list["Activity"]:
    dense  = dense_recall_sql(city, weekend, q_vec=embed(constraints.query))   # top-100
    sparse = sparse_recall_sql(city, weekend, q_text=constraints.query)        # top-100
    fused  = rrf([dense, sparse])[:100]                                        # 融合
    # 交叉编码重排：用"约束+偏好"作 query，候选活动文本作 doc
    pairs    = [(constraints.rerank_query(), a.rerank_text()) for a in load(fused)]
    reranked = bge_reranker.rank(pairs)          # cross-encoder 精排
    return reranked[:constraints.top_k]
```

### A.7 这如何兑现"不做半吊子"

- 召回来自**当周活动库**（每条带 evidence），不是静态热门 POI → 结构上避免"排列组合"；
- 重排以**用户约束 + 偏好**为 query → 个性化排序，不是千篇一律；
- 硬过滤 `verification_status` → 核心活动必是官方确认，不编造；
- **同一管线复用到餐饮**（v1 §9.4）：餐厅召回后按"**动线契合度(距离) + 偏好 + 忌讳**"重排，而非丢一个评分榜单——直接修掉"找餐馆不妥帖"。

## 增补 B（P0 仅证据可视；其余延后）结果的"清晰表达"，不是"酷炫交互"

**本阶段前端只有一个硬要求：把结果和证据状态展示清楚明白。** 一切"酷炫但重"的交互全部延后。

### B.1 必做（属"效果/可信"，不是美化）

- **证据六态视觉区分**：`estimated` / `unknown` 与 `confirmed` **必须一眼可辨**（不同底色/角标）。这是 PRD 硬 KPI"未确认误展为已确认 = 0"的**前端落地**，属**可信度**而非美化 —— 组件直接读 `evidence.verification_status` 决定样式（v1 §6.1 已定，此处升为 **P0 必做**）。
- **结构化卡片**：城市卡 / 交通卡 / 计划卡用**清晰信息层级 + 静态渲染**即可（标题、理由、待确认清单、来源角标）。**够用就好，不追动效。**
- **约束收集追问**：ConstraintParser 的主动追问用**简单选择题/文本**即可（对齐马蜂窝 AI 路书思路，但不需要花哨 UI），重点是补全缺失约束——属"效果"。

### B.2 明确延后（属"前端酷炫"，当前不投入）

- ❌ 预算滑杆实时联动改方案（飞猪）
- ❌ 双栏交互式地图（Mindtrip / Google Canvas）
- ❌ 行程节点拖拽 / 节点级编辑（飞猪）
- ❌ 手绘攻略图、拍照讲解等富媒体
- 地图：**探索阶段用静态图 / 一键直达高德链接**即可（复用 v1 §10 韧性表"生成一键直达地图链接"），不做嵌入式交互地图。

> 一句话：**先把"说得清、可信"做到位（证据可视 + 清晰卡片），把"用得炫"（滑杆/地图/拖拽）留到效果验证之后。** 这与"轻后端重证据"以及本阶段"关注效果"完全一致。

## 增补 C（P1，v0.2+）记忆 / 个性化分层：给 UserContext 一条演进路线

v1 只有一张 `UserContext` 表（§6.2）。《记忆框架调研》指出记忆分三层，各有对应方案与落地时机：

| 记忆类型 | 例子 | 方案 | 时机 |
|---|---|---|---|
| 会话工作记忆 | 本次预算/人数/已否决项 | **LangGraph checkpoint（已覆盖 ✅）** | v0.1 |
| 用户长期偏好 | 口味 / 出行半径 / 忌讳 | **Mem0**（中文可选 MemoryScope） | v0.2 |
| 跨会话演化事实 | 搬家 / 孩子长大 / 季节偏好变化 | **Graphiti**（双时间轴，可溯源） | v0.3 视需要 |

- **v0.1 保持现状**：`UserContext` 结构化表**足够**，**不引入记忆框架**（单组织者、避免过度工程）。
- **v0.2 引入偏好记忆的关键预警**（否则必踩坑）：新版 Mem0 是 **ADD-only**，会让"旧偏好、新偏好**同时被召回**"（stale/contradictory）。做偏好覆盖必须自建"**同键取最新 + 时间戳/阈值过滤**"，或选用带 UPDATE/DELETE 语义的经典算法版。
- **解耦原则**：活动/POI 走 RAG（增补 A），用户偏好走记忆层，二者**在 prompt 组装阶段合流**——不要把用户偏好塞进活动向量库。

## 增补 D（P1）配套技术栈接线：MCP / PydanticAI / 可观测

《Agent 框架选型》建议的分层配套，v1 未点名，补上（均属**工程质量/效果保障**，不是新功能）：

- **MCP 作为工具连接标准**：v1 的"统一 Provider 抽象"（§4.3）内部实现**即 MCP client**；地图/天气/航班/搜索逐步封装为 MCP Server。对齐 PRD v0.3"开放数据源插件机制"，也踩中行业趋势（途牛 CLI / 同程 MCP / 支付宝服务路由）。**落地节奏**：v0.1 先用普通 Provider 封装，工具增多再 MCP 化，**避免过度工程**。
- **PydanticAI / Pydantic 承载抽取**：LangGraph 节点内的抽取子调用（回填、活动字段）用 `output_type=Fact/Evidence` 直接产出**校验过的结构化事实**，与 Provenance Guard（§7.3）严丝合缝。预算小则用纯 Pydantic + Function Calling，不必引入新依赖。
- **可观测 LangSmith / Langfuse（OTel）**：给"未确认误展 = 0"这个硬 KPI 提供**埋点 + 回放**（v1 §11 说了埋点，此处点名工具）。框架无关，可随时接入。

## 增补 E（P2）LangGraph 编码补丁 + 可复用开源资产（来自 02 报告）

**① 状态字段加 reducer**（v1 §5.2 用的是普通 list，并行写会丢更新）：

```python
from typing import Annotated
import operator

class TripPlanState(TypedDict):
    # ... 其余字段不变
    activities: Annotated[list[dict], operator.add]   # 并行研究时追加合并
    warnings:   Annotated[list[str], operator.add]    # 多节点都可能追加告警
```

**② 探索阶段并行扇出**：多城市 / 多交通方式的门到门估算天然可并行（LangGraph `Send` 或并行节点 + reducer），显著降低探索版延迟。注意：**并行的是确定性计算 / 已就绪数据读取，不是实时抓取**（守住 v1 §4.2 读写解耦）。

**③ 依赖边必须"真连"**（`vikrambhat2` 反面教训）：`transport → await_booking → hotel → … → compose` 的数据必须真正流动，**禁止节点各自 →END**——否则"图"形同虚设，持久化/回退全部落空。

**④ 可复用开源资产**：
- 情报流水线（§8）的"找官方入口"检索层**直接复用 `gpt-researcher` pip 包**；但**事实抽取与定级必须走我们自己的证据管线**，不能直接拿它的报告当事实。
- 把 `RoamWise`（LangGraph 1.0 + 每步 HITL + Postgres 持久化 + "不自动下单"）当 v0.1 主干的**参考实现**来读。

## 结语

> **v1.1 = v1 主干不动 + 5 组增量。** 真正花力气的是**检索质量（增补 A）**——它把"当周活动驱动"这个差异化，从一句 PPT 口号变成"用户真觉得推得准"的产品力，也是唯一能正面回应竞品"半吊子 / 排列组合 / 找餐馆不妥帖"的地方。

前端在本阶段只需**清楚、可信**，不需要**炫**：证据状态一眼可辨、卡片信息清晰即可，其余交互留到效果被验证之后。这与"轻后端重证据"和你定的"先看效果"完全对齐。
