# 周末去哪儿：跨城周末出行决策 Agent 产品方案

> 一句话定位：根据同行人的时间、出发地、预算与兴趣，自动发现当周值得去的城市与活动，综合规划火车、飞机、住宿、市内交通和餐饮，生成一份可直接确认、分享和执行的周末出行方案。

---

# 1. 产品愿景

“周末去哪儿”要解决的，不是单纯的信息搜索问题，而是一个多人、多约束、跨平台的现实决策问题。

用户真正需要的不是：

- 再看一份城市榜单；
- 再刷一轮攻略；
- 再打开几个购票和地图 App；
- 再由一个人手工拼接所有信息。

用户真正需要的是：

> 在有限的周末时间里，从全国候选目的地中快速找到一个值得去、去得了、玩得好、吃得好、回得来的方案，并让同行人快速达成一致。

因此，产品不是传统旅游攻略工具，也不是单一票务或地图产品，而是一套面向周末场景的 **跨城出行决策与编排系统**。

---

# 2. 用户核心场景

## 2.1 目的地未知

用户只知道：

```text
这个周末想出去玩
预算每人 2,500 元
周五下班后出发
周日晚必须回到上海
想看展览、演出或城市特色活动
```

系统需要主动完成：

```text
全国当周活动发现
→ 候选城市筛选
→ 火车/飞机可达性判断
→ 住宿与市内交通粗估
→ 预算和有效游玩时间比较
→ 输出 3 个最值得去的方向
```

## 2.2 已指定目的地

例如：

```text
上海出发，周末去北京。
```

系统需要继续回答：

- 周五晚飞还是周六早高铁更合理？
- 周日返程坐飞机还是高铁更稳妥？
- 住在哪里能减少转场？
- 当周有哪些值得专程去的展览、演出或赛事？
- 午餐、晚餐怎样安排不影响活动和返程？
- 预算是否满足？
- 活动售罄或天气变化时怎么办？

## 2.3 多人不同出发地

例如三位同行人分别从：

- 浦东；
- 徐汇；
- 苏州；

出发前往北京。

系统需要计算：

- 每个人到机场或车站的时间；
- 是否适合同一车次或航班；
- 是否允许分别出发、目的地集合；
- 谁的通勤成本最高；
- 哪种方案对整个小组更公平。

# 3. 产品核心价值

## 3.1 从“找信息”升级为“完成决策”

现有产品通常只解决单点问题：

| 产品类型 | 解决的问题 |
|---|---|
| 内容社区 | 哪里好玩、哪里值得去 |
| 地图 | 怎么去、多久到 |
| 票务平台 | 买票 |
| OTA | 订机票、酒店 |
| 点评平台 | 吃什么 |
| 行程工具 | 把已确定的信息放进日历 |

“周末去哪儿”将这些环节串成一个连续闭环：

```text
发现
→ 比较
→ 确认
→ 编排
→ 分享
→ 执行
→ 重规划
```

## 3.2 从“单人推荐”升级为“多人协同”

多人出行的核心难点不是推荐，而是协调：

- 出发地不同；
- 时间不同；
- 预算不同；
- 有人愿意坐飞机，有人只愿意坐高铁；
- 有人想看展，有人更在意吃饭；
- 有人可以早起，有人不能接受红眼航班。

系统需要把偏好冲突转化为可比较的方案，而不是继续把选择交还给用户。

## 3.3 从“活动列表”升级为“完整周末方案”

产品最终推荐的对象不是一个活动，而是一个完整的 `Weekend Trip Bundle`：

```text
目的城市
+ 去程交通
+ 返程交通
+ 住宿区域
+ 核心活动
+ 市内交通
+ 午餐与晚餐
+ 时间缓冲
+ 总预算
+ 风险与备选
```

# 4. 核心产品流程

## 4.1 第一步：收集最小必要信息

首轮只询问：

```text
几个人？
分别从哪里出发？
最早什么时候能走？
最晚什么时候必须回来？
每人预算多少？
接受飞机、火车和过夜吗？
这周更想体验什么？
```

系统通过自然语言理解完成结构化，不要求用户填写复杂表单。

## 4.2 第二步：推荐候选城市

系统结合：

- 当周活动；
- 交通可达性；
- 门到门耗时；
- 有效游玩时间；
- 预算；
- 天气；
- 住宿便利；
- 餐饮吸引力；

生成 3 个候选方向。

示例：

```text
北京｜展览与城市文化
武汉｜演出与江城夜游
西安｜历史文化与特色餐饮
```

每个城市卡片展示：

- 为什么本周值得去；
- 推荐交通方式；
- 预计预算；
- 有效游玩时间；
- 主要风险；
- 当前需要确认的事项。

## 4.3 第三步：比较交通方案

系统对铁路、航空和混合方案进行统一比较。

不是只比较“飞行 2 小时”和“高铁 4.5 小时”，而是计算完整门到门成本：

```text
出发地到车站/机场
+ 候车/安检缓冲
+ 运行时间
+ 到达后的出站/取行李
+ 到酒店或首个活动
```

系统提供三类默认方案：

1. **时间优先**
2. **稳妥优先**
3. **预算与体验平衡**

## 4.4 第四步：确认交通和住宿

用户可通过：

- 手工输入；
- 粘贴文本；
- 上传查询截图；
- 浏览器扩展添加；

将已选择的车次、航班、酒店加入计划。

系统自动提取并让用户确认：

- 日期；
- 发到时间；
- 车次或航班号；
- 车站或机场；
- 价格；
- 酒店位置；
- 入住和退房时间。

## 4.5 第五步：生成完整行程

交通确认后，系统生成：

- 机场/车站接驳；
- 酒店入住与行李安排；
- 活动预约与游玩时间；
- 午餐、晚餐和休息点；
- 每段路线；
- 预算汇总；
- 返程缓冲；
- 主方案和备选方案。

## 4.6 第六步：分享与协作

组织者生成可分享计划卡，同伴可以：

- 查看方案；
- 确认是否参加；
- 填写自己的出发地和偏好；
- 对候选方案投票；
- 查看自己对应的交通建议。

计划卡默认不展示：

- 精确家庭地址；
- 个人预算上限；
- 证件信息；
- 私人偏好备注。

# 5. 核心功能设计

## 5.1 全国当周活动发现

活动是产品推荐目的城市的重要驱动力。

系统重点覆盖：

- 演唱会、音乐节；
- 戏剧、脱口秀、音乐会；
- 展览、博物馆特展；
- 体育赛事；
- 城市节庆、市集、快闪；
- 主题乐园和景区活动；
- 城市漫游与特色体验；
- 季节性活动；
- 地方特色餐饮活动。

每个活动至少包含：

```text
活动名称
城市与场馆
日期和开放时间
价格或预约说明
官方链接
来源等级
更新时间
当前确认状态
```

## 5.2 城市级目的地发现

系统维护高频周末目的城市目录，包括：

- 主要车站和机场；
- 核心活动区；
- 推荐住宿区域；
- 商圈与餐饮区；
- 城市公共交通特点；
- 典型周末主题；
- 季节性和天气特点。

动态活动搜索结果与城市基础能力结合，形成城市推荐。

城市评分综合考虑：

```text
当周活动价值
+ 交通可达性
+ 有效游玩时间
+ 总预算适配
+ 酒店和市内交通便利
+ 天气适配
+ 餐饮吸引力
- 延误和售罄风险
- 门到门时间惩罚
```

## 5.3 火车与高铁规划

系统提供：

- 适合铁路还是航空的判断；
- 推荐出发与返程时间窗；
- 高铁、动车、普通列车和夜间卧铺方案；
- 不同出发站和到达站比较；
- 起售提醒；
- 官方候补策略建议；
- 前后车次、邻近车站和交通方式备选；
- 购票后的车次回填和行程重排。

产品重点不是替用户购票，而是帮助用户判断：

```text
什么时候走最合理
选择哪类车次
夜间列车是否能增加有效游玩时间
返程车次是否会导致行程过赶
无票时应该放宽哪个约束
```

## 5.4 航班规划

系统提供：

- 多机场比较；
- 航班时间窗建议；
- 直飞与中转选择；
- 机场接驳时间；
- 行李、退改和航站楼检查清单；
- 航空与铁路门到门对比；
- 航班确认后的行程回填；
- 延误或价格变化后的备选调整。

对于上海到北京，系统会同时考虑：

- 虹桥与浦东；
- 首都与大兴；
- 周五晚出发；
- 周六早出发；
- 周日不同返程时段；
- 去程飞机、返程高铁等混合组合。

## 5.5 住宿区域决策

系统不只给酒店列表，而是先判断“住在哪个区域最合理”。

综合考虑：

- 到核心活动的时间；
- 到返程机场或车站的时间；
- 晚间餐饮和出行便利；
- 入住和退房时间；
- 行李寄存；
- 多人分房；
- 预算。

示例：

```text
推荐住宿：北京东四/王府井区域

原因：
- 到核心展览约 20–30 分钟；
- 周边餐饮密集；
- 周日晚前往北京南站较稳定；
- 适合晚到入住和次日步行游览。
```

## 5.6 市内交通规划

每个 Trip Bundle 都包含完整交通链路：

```text
家到车站/机场
→ 到达城市后前往酒店
→ 酒店到活动
→ 活动到餐厅
→ 餐厅到下一站
→ 酒店到返程车站/机场
```

系统计算：

- 预计时间；
- 距离；
- 换乘；
- 步行；
- 打车成本；
- 夜间公共交通风险；
- 天气影响；
- 时间缓冲。

## 5.7 餐饮规划

餐饮不是附加推荐，而是完整行程的一部分。

系统根据：

- 活动时间；
- 酒店和车站位置；
- 人数；
- 预算；
- 菜系偏好；
- 饮食禁忌；
- 用餐时长；
- 返程缓冲；

推荐：

- 午餐；
- 晚餐；
- 咖啡或休息点；
- 机场、车站或车上备选。

每个主餐提供：

- 推荐餐饮区域；
- 2–3 个候选；
- 与前后行程的距离；
- 人均价格；
- 营业时间；
- 预约建议；
- 一个稳妥备选。

## 5.8 天气与风险重规划

天气影响：

- 室内/室外活动排序；
- 步行时长；
- 交通方式；
- 餐饮和休息点；
- 活动替代。

系统在以下时间点重新检查：

- 方案生成时；
- 出发前 72 小时；
- 出发前 24 小时；
- 用户手动刷新时。

风险触发后，系统可：

- 替换活动；
- 减少户外行程；
- 调整交通；
- 重新安排餐饮；
- 更换目的城市；
- 切换为近郊或同城方案。

# 6. 产品输出形态

## 6.1 城市方向卡

```text
北京｜展览与城市文化

本周推荐理由：
- 有限时展览和周末文化活动；
- 室内体验丰富，天气适配性较高；
- 适合两天一夜。

推荐交通：
周五晚飞机 / 周六早高铁

预算：
约 2,100–2,900 元/人

有效游玩时间：
约 18–22 小时

主要风险：
周日晚返程交通紧张，核心活动需提前确认。
```

## 6.2 交通比较卡

```text
方案 A｜时间优先
周五晚飞，周日晚飞
优点：有效游玩时间最长
缺点：机场接驳和延误风险较高

方案 B｜稳妥优先
周六早高铁，周日晚高铁
优点：流程稳定、退改清晰
缺点：占用部分周六白天

方案 C｜综合平衡
周五晚飞，周日晚高铁
优点：兼顾游玩时间和返程稳定
```

周六

13:00 午餐
15:00 城市文化路线
18:30 晚餐

周日
09:30 第二活动
12:30 午餐

同时展示：

- 每段路线；
- 总预算；
- 已确认与待确认事项；
- 风险；
- 两个备选方案；
- 同伴分享入口。

# 7. 系统架构

产品采用一个状态化 Planner Workflow，而不是多个自由协作 Agent。

```text
Constraint Parser
→ Destination Discovery
→ Activity Research
→ Transport Strategy
→ User Confirmation
→ Hotel Area Planning
→ Local Mobility
→ Dining Planning
→ Timeline Solver
→ Feasibility Validator
→ Plan Composer
```

## 7.1 LLM 负责

- 理解自然语言需求；
- 提出必要追问；
- 从活动页面提取结构化字段；
- 分析用户偏好冲突；
- 解释方案取舍；
- 生成用户可读计划。

## 7.2 确定性服务负责

- 地理编码；
- 路线计算；
- 时间窗计算；
- 预算汇总；
- 硬约束校验；
- 候选排序；
- 提醒；
- 权限；
- 数据状态和来源管理。

系统不允许 LLM 自行编造：

- 航班；
- 车次；
- 票价；
- 余票；
- 活动时间；
- 营业时间；
- 实时空位。

# 8. 数据与知识体系

## 8.1 Activity Knowledge Layer

长期积累的核心数据资产包括：

```text
活动来源注册表
+ 当周活动结构化库
+ 场馆与主办方目录
+ 城市活动日历
+ 来源可信度
+ 数据更新时间
+ 重复活动识别
+ 过期下架
+ 人工审核后台
```

## 8.2 City Playbook

每个核心城市维护一份可复用的周末知识：

- 主要交通枢纽；
- 活动聚集区；
- 住宿区域；
- 餐饮区；
- 典型两日路线；
- 雨天方案；
- 夜间交通；
- 返程风险；
- 适合的旅行主题。

## 8.3 用户个人上下文

在用户授权后保存：

- 常用出发城市；
- 可接受预算；
- 飞机/铁路偏好；
- 常见同行人；
- 活动兴趣；
- 饮食限制；
- 过去去过的城市和活动。

这些信息用于减少重复询问和提高下一次规划质量。

# 10. 核心指标

## 北极星指标

```text
每周被用户确认的可执行 Weekend Trip Bundle 数
```

## 关键漏斗

```text
发起规划
→ 完成约束输入
→ 查看候选城市
→ 选择目的地
→ 确认交通
→ 生成完整计划
→ 分享
→ 自报实际出行
```

## 产品质量指标

- 候选城市采纳率；
- 最终计划确认率；
- 从开始规划到确认方案的时间；
- 核心活动官方来源覆盖率；
- 过期信息率；
- 日程硬冲突率；
- 门到门时间偏差；
- 总预算偏差；
- 分享率；
- 次周复用率。

# 11. 核心差异化

## 11.1 不以票务或内容为中心，而以决策为中心

产品不替代票务、地图或内容社区，而是把它们连接成一个完整决策过程。

## 11.2 目的地由当周活动驱动

系统不是只推荐热门城市，而是回答：

> 为什么这个周末值得去这座城市？

## 11.3 统一比较铁路和航空

真正比较门到门时间、有效游玩时间和总成本，而不是只看票面历时。

## 11.4 交通、住宿、活动和餐饮联合排程

每个推荐都是完整 Bundle，不是多个互相冲突的独立列表。

## 11.5 多人协作与公平性

系统将同行人的不同出发地、时间和预算纳入同一个方案，而不是只优化组织者个人体验。

## 11.6 可信来源与确认状态

每项信息清楚区分：

```text
官方已确认
用户已确认
公开来源观察
系统估算
待确认
已过期
```

# 12. 最终产品表达

“周末去哪儿”不是一个攻略生成器，也不是一个新的票务平台。

它是一套能够回答以下问题的周末旅行决策系统：

```text
这个周末去哪座城市最值得？
为什么是现在去？
坐火车还是飞机？
什么时候出发才能玩得最完整？
住在哪里最少折腾？
哪些活动值得专程去？
吃饭安排在哪里不会耽误返程？
多人意见不一致时怎么折中？
计划变化后怎样快速重新安排？
```

最终，用户得到的不是一段旅行建议，而是一份：

> **值得去、去得了、安排合理、同行人愿意接受、可以直接执行的完整周末方案。**
