# 「周末去哪儿」产品方案

**一个跨平台的周末决策与协作 Agent**

版本 v3.0 · 2026 年 7 月

---

# 01 我们看到的真问题

周末跨城出行的人越来越多，但决策体验还停留在十年前。

用户并不缺少购票 App。12306、航司、携程、美团，每一个都把自己的环节做得很好。真正缺的是**跨 App 的决策和组织能力**：

```text
不知道这个周末去哪
不知道这个周末有什么值得专门跑一趟的活动
不知道坐飞机还是火车更合理
不知道票买完之后一天怎么排
不知道住哪里最省转场
不知道吃饭安排在哪里不会耽误返程
不知道怎么让同行人快速达成一致
```

一次周末出行，决策链条割裂在六七个 App 之间：在一个 App 里刷目的地灵感，在另一个 App 里查票，在群里争论，在地图里算路线，最后在备忘录里手工拼出一份谁也不知道准不准的"行程单"。

「周末去哪儿」要解决的就是这件事。

# 02 产品定位

## 一句话定位

> 输入大家的时间、出发地和预算，系统帮你找到这个周末值得去的城市和活动，给出火车/飞机的选择框架，并把你在官方平台选好的票、酒店和活动，整合成一份可以直接发群执行的计划。

## 我们刻意不做交易

「周末去哪儿」不是又一个旅游交易平台，而是**位于所有交易平台之前和之间的决策层**：

```text
搜索/决策层（我们） → 官方交易平台（12306/航司/OTA/商家） → 行程整合层（我们）
```

不做交易是一个主动的战略选择，它带来三个产品级的结果：

- **中立。** 我们不从任何一笔订单里抽成，推荐逻辑只服务于"这个周末怎么过最值"，而不是"卖什么库存"。
- **完整。** 火车、飞机、酒店、活动、餐饮可以出现在同一份计划里，不偏袒任何一个平台。
- **轻。** 交易、售后、退改留在最擅长的官方平台，我们把全部精力放在决策质量上。

## 产品的护城河

我们的壁垒不是库存，而是决策智能：

- 当周活动的可信调研与结构化；
- 跨城市候选的比较能力；
- 火车/飞机的门到门决策（算上接驳、缓冲和有效游玩时间，而不只是票面时长）；
- 用户已订订单的自动结构化；
- 活动、交通、住宿、餐饮的联合排程；
- 多人约束下的群体决策；
- 贯穿全程的信息证据与不确定性表达。

# 03 四大设计原则

## 原则一：当周即研（Just-in-time Research）

周末产品的价值单位不是"全国"，而是"这个周末"。

我们不维护一个庞大但陈旧的静态数据库，而是在你规划某个具体周末时，即时调研当周正在发生的展览、演出、市集和赛事。**新鲜感就是准确性**——一个周末产品的核心资产，是"此刻值得去"的判断力。

## 原则二：开放连接（Deep Link, not Transaction）

查票去 12306，买机票去航司或你信任的 OTA，订座去商家官方页面。我们为每一步生成精准的官方入口和查询策略，用户一键跳转到权威页面完成交易。

我们与所有平台是协作关系，不是竞争关系。

## 原则三：你的订单即数据（Bring Your Own Booking）

你在任何平台订好的票、房、活动，都不该手工抄进行程。粘贴一段订单文本、上传一张截图、或丢进来一个链接，系统自动识别并结构化为计划的一部分——车次、发到站、时间、席别、价格，逐一提取，经你确认后汇入总行程。

这是"以用户已有资产为中心"的设计：产品不圈住用户，而是汇入用户已有的数字生活。

## 原则四：证据优先（Evidence First）

每一条活动、营业时间、价格、交通信息都标注**来源、更新时间和确认状态**；系统不知道的事，就明确说不知道，绝不让 AI 编造一个看似漂亮的答案。

在 AI 生成内容泛滥的时代，可信是被设计出来的。这是我们最重要的交互承诺。

# 04 核心体验：两段式规划

真实的周末决策从来都不是一次完成的：大家先商量去哪，再去订票，票定了才能排精确日程。「周末去哪儿」把这个真实习惯做成了产品结构——**先探索，后确认**。

## 第一阶段：探索方案

输入约束后，系统输出：

- 3 个候选目的城市及当周亮点；
- 每个城市值得去的活动；
- 建议交通方式（高铁/飞机/都值得比较）；
- 建议出发与返程时间窗；
- 预计门到门耗时与粗略预算；
- 一份"待你确认"清单。

## 第二阶段：确认方案

当你在官方平台查好或买好票、选定酒店并回填后，系统才输出：

- 精确到小时的行程时间线；
- 机场/车站接驳方案；
- 入住、寄存行李安排；
- 活动预约时间；
- 午晚餐地点与饭点；
- 返程缓冲与可执行备选。

两阶段设计让产品始终诚实：交通未确认前，它给你决策框架；交通确认后，它给你可执行计划。**它从不假装知道下一秒会变的库存数字**——这是产品的可信边界，也是体验设计的一部分。

# 05 功能设计

## 5.1 周末约束收集

规划从一份轻量的约束清单开始：

- 组织者出发城市和大致位置；
- 同行人数及各人所在城市或商圈；
- 最早出发、最晚返回时间；
- 人均预算；
- 是否允许过夜、是否接受飞机、是否接受夜间列车/卧铺；
- 活动偏好、强约束与饮食禁忌。

**多人协作**：组织者可以发出一个匿名邀请链接，每位同伴只需填自己的出发地、时间、预算范围和偏好。系统默认只向群里展示**聚合结果**——不暴露任何个人的预算数字和精确位置。群体决策，不该以牺牲个体隐私为代价。

## 5.2 目的地发现

目的地推荐采用两层结构：

**第一层：精选城市目录。** 首批深度维护 15–20 个高频周末城市（上海、北京、杭州、苏州、南京、成都、重庆、西安、武汉、长沙、广州、深圳、厦门、青岛、天津等）。每个城市预置结构化的"城市档案"：主要车站与机场、典型住宿区域、核心商圈与文化区、官方活动来源、公共交通特点、周末适配标签、季节性风险。

**第二层：当周活动动态调研。** 按你的偏好即时搜索：

```text
北京 + 本周末 + 展览
成都 + 本周末 + 音乐节
杭州 + 本周末 + 市集
```

活动价值 × 交通可达性，组合成最终的城市推荐。

**城市卡片**长这样：

```text
北京｜展览与城市文化

为什么本周值得去：
- 某官方场馆正在举办限时展览
- 周六和周日均开放
- 雨天影响小

交通建议：
- 优先比较周五晚航班和周六早高铁
- 推荐去程 18:30–22:30，返程 17:00–21:00

当前待确认：
- 实际机票/车票价格 · 活动余票 · 酒店房态
```

## 5.3 活动情报系统

这是产品最值得长期建设的资产。

**来源按可信度分级**：

1. 主办方、场馆、博物馆、剧院、体育馆官方网站；
2. 城市文旅局与公共文化日历；
3. 开放活动数据接口（覆盖地区适用时）；
4. 搜索发现（仅用于找到入口，核心事实回到官方来源核实）；
5. 用户提供的活动链接；
6. 人工精选；
7. 内容社区仅作灵感线索，不作为唯一证据。

**每条活动都是一条带证据的结构化记录**：

```json
{
  "title": "活动名称",
  "city": "北京",
  "venue": "场馆",
  "start_at": "2026-07-18T10:00:00+08:00",
  "price_text": "官方页面展示价格",
  "booking_url": "官方链接",
  "source_type": "official_venue",
  "fetched_at": "…",
  "verification_status": "official_confirmed",
  "availability_status": "user_must_confirm"
}
```

后台是一套完整的情报流水线：来源注册表、调度器、页面提取、活动归一化、实体对齐、去重、过期清理、证据库与人工审核台。只采集明确允许访问的官方公开信息，低频、克制、尊重站点规则。

## 5.4 火车/高铁：策略，而不是赌运气

**A. 交通方式判断。** 根据城市距离和你的时间窗，判断高铁优先、卧铺可选、飞机优先，还是两者都值得比较。

**B. 查询策略卡。** 系统不替你刷票，而是告诉你**该去查什么、为什么**：

```text
上海 → 北京

建议查询：
- 周五 18:30 后出发的夜间列车/卧铺
- 周六 06:00–08:00 高铁
- 周日晚 17:00–20:00 高铁返程

为什么：
- 周六早高铁会占用大部分白天
- 夜间列车能提高有效游玩时间
- 周日晚返程需要保留进站缓冲
```

**C. 官方入口。** 一键直达 12306 官方渠道，附带操作提示。

**D. 起售提醒。** 热门周末线路拼的是手速。系统根据官方预售规则生成起售提醒（预计值会明确标注"以 12306 当前页面为准"），提醒里附好预填信息、候补建议和备选车次清单——到点你只需要点几下。

**E. 一键回填。** 手工输入、粘贴文本、上传截图，三种方式把已查/已购车次汇入计划，识别结果经你确认后生效。

**F. 无票策略。** 没票时系统给出的是一套行动选项而非一句"抱歉"：官方候补、前后车次、同城异站、卧铺替代、改飞机、改目的地、调整行程长度。

## 5.5 飞机：算的是门到门

**A. 飞行可行性判断。** 票面飞行时间只有两小时，不代表它更快。系统综合计算：出发地到机场的时间、值机缓冲、目的地机场到活动区的时间、周末有效游玩时间，给你一个**门到门**的诚实的比较。

**B. 航班查询策略。**

```text
上海 → 北京

建议优先查询：
- 周五 19:30–22:30 起飞
- 周六 06:30–08:00 起飞
- 周日晚 18:00–21:00 返程

机场：
- 上海同时比较虹桥与浦东
- 北京同时比较首都与大兴

重点检查：
- 是否含托运行李 · 退改规则 · 航站楼 · 实际落地时间
```

**C. 你信任的比价入口。** 航司官网、OTA、Google Flights、Skyscanner——入口由你选，我们不碰你的账户。

**D. 航班回填。** 与铁路一致，粘贴或截图，确认即入计划。

## 5.6 住宿：先定区域，再定酒店

好的住宿决策 80% 是区域决策。系统负责：

- 根据活动位置和返程车站/机场，推荐住宿区域；
- 比较"住核心活动区、交通枢纽区还是中间地带"；
- 估算各区域到活动和车站的时间；
- 生成筛选清单和平台搜索入口；
- 接收你选定的酒店，把入住、退房、行李寄存编入时间线。

**住宿区域卡**：

```text
建议住宿：东四/王府井区域

原因：
- 到核心展览约 20–30 分钟
- 晚餐选择多
- 周日去北京南站相对稳定

筛选条件：
- 周五 23:30 后仍可入住
- 可免费取消 · 可寄存行李
- 两间房总价不超过 1,200 元
```

## 5.7 餐饮：安排在动线上，而不是榜单上

餐厅推荐服务于行程动线：根据活动和返程时间安排饭点，在正确的位置给出 2–3 个候选，标注菜系、预算、饮食限制、营业时间和公开电话，并永远附带一个稳定备选。

你还可以粘贴自己在点评、小红书里收藏的链接——系统把它接入候选池，完成位置对齐和路线计算。**你收藏夹里的店，第一次真正进入了你的行程。**

## 5.8 市内交通与接驳

基于地图服务完成地址解析、POI 搜索、公交/步行/驾车路线与距离矩阵计算，把"机场→酒店→展览→晚餐→车站"的每一段接驳都排进时间线。探索阶段用粗略距离控制成本，城市确定后再算精确路线。

## 5.9 天气感知与智能重规划

天气是概率信号，直接参与排程决策：

```text
降水概率高   → 室外活动降权，增加室内备选
高温        → 减少长距离户外步行，安排午后室内休息
强对流/预警  → 不推荐高风险户外活动
```

当天气变化或你更新了任何信息，系统在重新打开计划、出发前检查、手动刷新时触发重规划——计划是活的，但只在有意义的时刻打扰你。

# 06 Trip Bundle：一份可以直接发群的计划

所有决策最终收敛为一份 Trip Bundle。

**探索版**（交通确认前）：目的地、主题、推荐交通方式、去返程时间窗、预算区间、核心活动、住宿区域、待确认清单。

**确认版**（回填完成后）：完整活动、餐饮、市内路线、逐小时时间线、已确认花费、预估待花费用、风险提示与备选方案。

贯穿始终的是我们的**信息状态体系**——每个字段都带六种状态之一：

```text
confirmed_by_user        用户已确认
official_source_confirmed 官方来源确认
public_source_observed   公开来源观察到
estimated               估算值
unknown                 未知
expired                 已过期
```

界面上，估算值和已确认值永远长得不一样。用户不必猜"这个数字到底准不准"。

# 07 浏览器扩展：跨平台体验的最后一公里

我们为重度用户准备了一个可选的浏览器扩展。当你在 12306、航司官网、OTA、酒店页或票务页浏览时，点一下"添加到周末计划"——扩展会读取你**当前正在查看并主动选择的字段**，在本地生成结构化草稿，经你确认后汇入行程。

安全与隐私是这条功能的第一约束：

- 不自动登录，不模拟购票；
- 不读取密码与支付信息；
- 不做后台批量抓取；
- 默认本地解析，用户确认后才提交。

它把"回填"从一分钟缩短到一秒，但永远只是增强，不是依赖。

# 08 提醒系统

一份好计划的时间价值，一半在提醒里：

- 火车票起售提醒；
- 活动预约开放提醒；
- 机票复查提醒；
- 行前 72 小时确认；
- 行前 24 小时天气检查；
- 出发前交通与证件检查；
- 酒店免费取消截止时间；
- 活动开场与返程提醒。

提醒通过 Web Push、邮件、ICS 日历订阅送达——其中 ICS 零平台依赖，一键进系统日历。

# 09 韧性设计

真实世界里任何外部服务都会波动。产品的设计目标是：**任何单点失效，用户仍然拿到一份有用的输出。**

| 场景 | 产品表现 |
|---|---|
| 搜索服务不可用 | 输出搜索关键词与官方来源清单，用户粘贴链接继续 |
| 官方页面结构变化 | 展示链接，请用户确认时间与价格 |
| 地图额度受限 | 启用缓存，生成一键直达的地图链接 |
| 交通未确认 | 只输出时间窗与策略，不生成伪精确日程 |
| 活动余票未知 | 明确标注，且不作为唯一核心活动 |
| 酒店未定 | 输出住宿区域与筛选条件 |
| AI 服务异常 | 规则模板兜底，生成简化计划 |
| 跨城方案均不成立 | 自动转向近郊或同城方案 |

# 11 我们如何衡量成功

**产品价值指标**

- 用户能否在 15 分钟内从"没有目的地"收敛到 1 个候选城市；
- 交通回填完成率；
- 最终计划确认率与分享率；
- 从启动规划到方案确认的总时长；
- 次周再次使用率。

**可信度指标**

- 核心活动拥有官方来源的比例；
- 过期活动率；
- 未确认字段被错误展示为已确认的次数——**必须为 0**；
- 位置匹配准确率、回填解析准确率；
- 日程硬冲突率。

最后一条指标值得单独强调：在这个产品里，"诚实"不是价值观口号，而是一个有硬性 KPI 的工程目标。

---

# 12 技术架构简述

- **形态**：移动端优先的 Web/PWA；
- **编排**：显式状态机驱动规划流程（收集约束 → 目的地发现 → 等待交通确认 → 生成最终计划 → 确认/重规划），每一步的状态对用户可见、可回退；
- **AI 使用**：小模型做信息抽取，大模型只做复杂调研与解释；敏感位置与订单字段脱敏后才进入模型；支持用户自带模型 Key，数据主权在你手里；
- **信息采集**：仅面向官方公开来源的低频白名单采集，尊重站点规则，搜索结果一律回到官方来源核实；
- **架构哲学**：轻后端、重证据。服务器成本让位于数据可信度建设。

# 结语

旅游产品的上一代战争发生在"交易"上——谁的库存多、价格低。而下一代机会在交易之前的 48 小时：**帮一群人决定这个周末怎么过。**

「周末去哪儿」选择站在用户一边，做那个中立、诚实、把碎片信息缝合成一份好计划的决策层。
