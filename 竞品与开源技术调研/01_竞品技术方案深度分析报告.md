## 1. 执行摘要

| 产品 | 技术形态一句话 | 与我们的核心差异 | 最值得借鉴的一点 |
|---|---|---|---|
| **飞猪 问一问** | 通义千问多模型 + **多智能体编排（orchestrator-worker）** + 实时报价引擎 | 交易闭环、绑自家库存 | 把"专业定制师工作流"固化为智能体分工与思维链 |
| **携程 问道 / TripGenie** | **旅游垂直大模型** + "可靠答案库" + 经典 NLP 客服管线 | 交易闭环、重训练 | 用结构化"可靠答案库"约束生成、抑制幻觉 |
| **马蜂窝 AI 小蚂 / AI 路书** | DeepSeek + **垂直精调"质检员"双模型** + UGC 知识图谱 | 内容生态驱动、绑自家 UGC | **双模型交叉验证 = "有据可依"**；主动提问补全需求 |
| **同程 程心 AI** | 旅游专属大模型 + DeepSeek + **智能体直连实时业务数据池** | 对话式交易闭环 | Agent 直连实时数据池的工程解耦思路 |
| **支付宝 出行助手** | 通用智能体平台 + 服务聚合（小程序生态） | 服务聚合、绑支付/生态 | 跨服务"聚合编排"的入口整合 |
| **豆包 / DeepSeek / 元宝 等** | 通用大模型 + 联网搜索 | **无实时数据、爱编造** | 反面教材：印证"护栏必须是架构级" |
| **Mindtrip / Layla / Wanderlog** | LLM + POI 库 + 地图 + RAG grounding | 偏静态攻略、面向境外 | 交互式地图 + POI grounding 的前端表达 |
| **TripIt** | **多格式预订邮件解析引擎**（规则+ML+LLM） | 只做行程归集、无决策 | **"回填/BYO Booking"的鼻祖**，解析管线值得深挖 |

**一句话结论**：所有头部对手都赢在"实时数据 + 编排"，但都**绑定交易、推荐向库存倾斜**；通用大模型输在"无实时数据、爱幻觉"。**"中立决策层 + 证据优先"是一块被集体让出的空位**——但代价是我们拿不到实时库存，必须用"策略卡 + 深链 + 回填 + 证据体系"去补。这条边界正是本产品的护城河，也是最难的工程。

## 2. 行业全景与权威评测坐标系

### 2.1 北二外《AI 旅游行程助手类应用能力评测报告》（2025-11）

这是国内首份系统性评测，为整个赛道提供了权威坐标系，其**分类法与指标体系**对我们定义产品边界极有价值。

**四类玩家（按技术形态分）：**

```text
交易闭环型   OTA 平台（飞猪、携程、同程）—— 实时库存 + 一键下单
内容生态型   泛生活/内容平台（小红书点点、马蜂窝）—— UGC 驱动
信息生成型   通用大模型（豆包、元宝、DeepSeek）—— 联网搜索 + 生成
服务聚合型   通用智能体平台（支付宝出行助手）—— 小程序/服务编排
```

> **本产品的定位**：我们不属于上述任何一类，而是**"决策编排型"**——站在四类之前的**中立决策层**。这个类目目前是空白。

**五大维度、24 项三级指标：**

```text
可用性   信息与服务的准确性、完备度   ← 我们的"证据优先"直接服务这一维度
易用性   交互门槛与操作效率
个性化   需求理解与方案定制精准度       ← 我们的"约束收集 + 多人聚合"
流畅性   多轮对话与任务执行无缝体验
安全性   数据隐私与内容合规             ← 我们的"不碰交易 + 脱敏 + BYO Key"
```

**评测排名（满分 900，均分 689.49）：**

```text
飞猪问一问 724.92  >  同程程心AI  >  支付宝出行助手  >  小红书点点
>  携程问道  >  腾讯元宝  >  字节豆包  >  DeepSeek
```

**两个关键行业信号：**

1. **"强于内容推荐，弱于执行落地"**——全行业的通病。这恰好是我们两段式设计（探索版→确认版）要正面解决的：我们不假装能"执行"（下单），而是把"落地"交还官方平台 + 回填。
2. **OTA 产品与通用大模型分差近 100 分**，差距核心就是**"实时数据 + 成熟服务生态"**。这印证了我们矩阵中的判断：没有实时库存，就必须用"策略卡 + 回填 + 证据"补上可信度，否则会掉进通用大模型的"幻觉深坑"。

## 3. 国内 OTA 内嵌 AI 助手

### 3.1 飞猪「问一问」——多智能体编排的标杆（评测第一）

**基本事实**（2025-04-17 上线，集成通义千问多个主力模型）：

- 定位"管家型旅行 AI"，四大核心模块：**目的地探索、机票比价、行程规划、酒店推荐**。
- 智能体团队：**行程助手、路线定制师、智慧交通顾问、酒店顾问、攻略达人、本地人导游、预算管理师、服务保障专员**。

**技术架构（orchestrator-worker 多智能体模式）：**

```text
用户自然语言（支持文字/语音/方言，多模态输入）
        │
        ▼
┌──────────────────────────────────────────────┐
│  行程助手（Orchestrator）                       │
│  分析需求 → 判断需唤起哪些 worker → 汇总输出      │
└───────┬──────────────────────────────────────┘
        │ 分派（自主决策）
   ┌────┼─────────┬───────────┬──────────┐
   ▼    ▼         ▼           ▼          ▼
智慧交通  酒店顾问   路线定制师   攻略达人   （并行执行）
顾问      │         │           │
   │      │         │           │  各自调用飞猪实时供应链数据
   └──────┴────┬────┴───────────┘
               ▼
        预算管理师（汇总核算费用）
               ▼
        行程助手 → 输出方案（图片+商品卡片+景点链接+手绘攻略）
```

**从产品行为反推的关键实现：**

- **机票比价**：华创证券披露其采用**多目标优化模型**，实时抓取航司数据，输出"结构化比价卡 + 中转动线图 + 旅行贴士"，形成"比价-解析-决策"闭环。→ **这是确定性优化 + LLM 解释的分工**，与我们的"门到门确定性计算 + LLM 解释取舍"思路一致，但他们优化的是"卖哪张票"，我们优化的是"这个周末怎么过"。
- **酒店推荐**：**过滤差评率 > 10% 的酒店**，生成"性价比/高分/高端"三档差异化方案，用"优势标签-用户口碑-价格波动"三维对比表。→ 典型的**规则过滤 + 结构化卡片**，非纯生成。
- **目的地探索**：深度语义解析 + 时间适配 + 预算约束 + 用户画像 → 调实时供应链数据 + 内部 UGC → 结构化推荐。→ 与我们的 `DestinationDiscovery` 节点高度相似，差异在数据源（他们用自家库存，我们用当周活动 + 城市档案）。

**抑制幻觉的手段**：整合"旅行社/专业定制师工作流 + 平台实时供应链 + 服务评价"打造垂类数据集，**用垂类数据降低基础模型幻觉率**。技术负责人明确提到"将定制师知识经验融入 AI 的分析/执行/决策节点，提升**思维链**效率"。

> **对我们的启发（正向）**：
> 1. **orchestrator-worker 分工**值得借鉴，但我们用 **LangGraph 显式状态机**而非隐式多智能体自由协作——因为我们要"每步可见、可回退、可中断"，自由协作难以满足两段式与人在环。
> 2. **"把专业工作流固化成流程"**：飞猪固化了定制师工作流，我们应固化"周末跨城决策工作流"（约束→发现→交通→回填→排程）。
> 3. **结构化卡片而非纯文本**：比价卡、对比表、动线图——我们的城市卡/交通卡/计划卡也应如此。
>
> **对我们的警示（反向）**：飞猪的"实时报价 + 一键预订"是我们**主动放弃**的能力。我们不能、也不应模仿其交易闭环；我们的价值在其**不做的地方**（中立、跨平台整合、证据透明）。

### 3.2 携程「问道」+ TripGenie——垂直大模型 + 可靠答案库

**技术事实：**

- **携程问道**（2023-07 发布，行业首个旅游垂直大模型）：基于**200 亿高质量非结构性旅游数据**自研训练，**结合平台结构性实时数据 + 历史机器人/搜索算法**，构建**"可靠答案数据库"**。
- **TripGenie**（AI 旅行助手）：LLM 生成个性化行程、即时预订、9 语种、行中实时监控调整、拍照翻译菜单、行李清单、行程提醒——**图文+卡片+链接+地图**混合表达。订单转化率翻倍。
- 研发投入巨大：单季度约 30–36 亿元，占净营收约 23–27%。

**AI 客服的经典 NLP 管线（可推断问道的意图理解也复用类似栈）：**

```text
NLP:  领域分类（机票/酒店/火车票…）→ 意图识别 → 槽位解析（时间/地点/人数）
ML:   意图识别用 Bi-LSTM / Transformer；对话管理用强化学习
ASR/TTS: 语音输入输出
兜底:  无法解决 → 自动生成工单转人工
```

**设计洞察：**

- **"可靠答案库"是携程抑制幻觉的核心手段**——先用结构化/半结构化的可信答案约束生成，而非让大模型自由发挥。这与我们的**证据库 + Provenance Guard** 目标一致，但实现路径不同：携程靠"自训垂直模型 + 内部答案库"（重资产），我们靠"外部官方来源 + 字段级来源白名单 + 状态标注"（轻资产）。
- **重训练路线**（自研垂直大模型）成本极高，只有携程这种体量的 OTA 玩得起。**我们不走重训练路线**——技术方案已明确"能确定性算的交给服务、需要理解的交给分层通用 LLM + 护栏"，这是资源约束下的正确选择。

> **对我们的启发**：把"可靠答案库"降维成**"证据库 + verification_status 定级"**——我们不需要 200 亿数据训练模型，只需要为 15–20 个城市维护高质量官方来源，就能在**周末跨城**这个窄场景内达到可信。**窄场景是小团队对抗大厂的唯一路径。**

### 3.3 马蜂窝「AI 小蚂」+「AI 路书」——双模型质检 = 与我们最像的"证据优先"

**这是与本产品理念最接近的竞品**，值得重点拆解。

**技术架构（双模型 / 质检员架构）：**

```text
用户需求
   │
   ▼
DeepSeek 大模型  ──生成推荐──►  马蜂窝垂直精调模型（"质检员"）
                                    │
                                    │ 用经检验的攻略/游记数据库交叉验证
                                    │ 结合定制师/指路人专业信息
                                    ▼
                              确保信息准确 → "有据可依"输出
```

- **全量接入 DeepSeek + 自研垂直精调模型**，后者"如同严谨的质检员"：当大模型生成推荐时，精调模型**立即通过马蜂窝攻略/游记等经检验的数据库内容交叉验证**，确保准确。
- 官方原话：**"旅行是最不能容忍幻觉的领域……双模型架构，让 AI 既有秒问秒答的效率，又有脚踏实地的可靠性。"**
- 数据底座：亿级真实游记/笔记，覆盖**全球 6 万+目的地、6300 万 POI**，构建旅游行业"知识图谱"。
- **AI 路书**的交互创新：不同于"提交即思考"的产品，**AI 路书先"主动提问"**——用选择题形式帮用户"查漏补缺"，由 AI 重新整理需求、交用户确认后再进入研究定制流程。
- **动态地图**：显示当天路线长度、是否走回头路、景点衔接；点击 POI 可看真实 UGC，"杜绝照骗"。

**设计洞察（三点直接映射到我们）：**

| 马蜂窝做法 | 「周末去哪儿」对应设计 | 异同 |
|---|---|---|
| 双模型"质检员"交叉验证抑制幻觉 | Provenance Guard 三闸 + 证据状态定级 | **同目标，不同实现**：他们用第二个模型质检，我们用**确定性规则 + 来源白名单**质检（更便宜、更可解释、CI 可断言） |
| "有据可依"、点击 POI 看真实 UGC | Evidence First、每字段带 source_url/fetched_at/verification_status | **同哲学**：都拒绝"看似漂亮的编造" |
| AI 路书"先主动提问"补全需求 | ConstraintParser 追问补全 + 约束收集向导 | **同交互模式**：都反对"表单填一堆"，主张对话式渐进澄清 |

> **对我们的启发（关键）**：马蜂窝证明了**"证据优先/双重校验"在旅游场景是被验证的价值主张**，不是我们的一厢情愿。差异在于：
> - 他们**绑定自家 UGC**（数据护城河来自内容生态），我们**中立地指向官方来源**（护城河来自跨平台整合与证据透明）；
> - 他们用"第二个模型"质检（推理成本翻倍），我们用**确定性护栏 + 字段级来源策略**质检——**更适合小团队的成本结构**。
>
> **可直接借鉴**：AI 路书的"先主动提问、选择题补全、用户确认"交互，几乎就是我们 `ConstraintParser` + 约束收集向导应有的样子，可作为 UX 参考基线。

### 3.4 同程「程心 AI」——智能体直连实时业务数据池（评测第二）

- 旅游专属大模型，**2025-03 与 DeepSeek 技术融合**，推"AI + 实时预订"。
- 三大核心能力：**智能行程生成、自适应推荐系统、对话式交易闭环**。
- 官方技术思路原话：**"不仅依靠基础大模型知识，还通过智能体架构，深度接入同程旅行庞大的实时业务数据池。"**
- 覆盖从信息咨询 → 资源检索 → 决策分析 → 预订的全链路。

> **对我们的启发**：程心的"**Agent 架构直连实时数据池**"在工程上验证了"编排层与数据层解耦"的必要性。我们的架构（4.2 两条数据流：规划请求流 vs 情报生产流）走的是同一思路——**规划时只消费预热好的数据，不做实时抓取**。差异：他们连的是自家库存池（可下单），我们连的是**预热的活动证据库 + 确定性服务**（不可下单，但中立）。

### 3.5 支付宝出行助手 / 小红书点点（评测第三、第四）

- **支付宝出行助手**：属"服务聚合型"，依托**通用智能体平台 + 小程序生态**，把打车/火车/机票/景区等服务聚合编排在一个入口。优势是**支付与生态闭环**，劣势是深度决策弱、绑支付宝生态。
- **小红书点点**：属"内容生态型"，**在垂直场景体验突出**（种草→决策），护城河是海量真实内容与社区信任，但执行落地（交通/预订）弱。

> **对我们的启发**：这两者代表两种"入口"策略——**服务聚合**（支付宝）与**内容种草**（小红书）。我们既非入口也非内容社区，而是**决策编排**；但小红书的"内容作为灵感线索"恰是我们 PRD 明确的低优先级来源（内容社区仅作灵感、不作唯一证据），边界要守住。

## 4. 通用大模型 / Chatbot

### 4.1 事实与评测结论

- 评测排名靠后：**腾讯元宝 > 字节豆包 > DeepSeek**（均在 OTA/聚合型之后）。
- 评语：**"交互自然，但个性化推荐、多模态能力短板明显"**，与 OTA 产品分差近 100 分。
- 行业已出现**"第一批 AI 旅游受害者"**：通用 chatbot 编造不存在的车次、航班、票价、营业时间，用户按其规划出行踩坑。

### 4.2 技术根因（这正是我们的护栏设计动机）

```text
通用大模型旅行规划的失败链：
  参数化知识过时  +  联网搜索结果无来源约束  +  无确定性交通/时间计算
        │                     │                        │
        ▼                     ▼                        ▼
  编造"看似合理"的车次/航班   把搜索片段当事实      门到门时间靠"感觉"
        └─────────────► 生成一份漂亮但不可执行/危险的行程
```

**这些正是本产品用架构级手段规避的：**

| 通用模型的坑 | 我们的架构级对策（技术方案对应节） |
|---|---|
| 编造车次/航班/票价 | **Provenance Guard 三闸**：字段级来源白名单，LLM 不在交通/票价字段白名单内（§7.3） |
| 把搜索片段当事实 | 搜索**仅用于找官方入口**，事实回官方核实（§2.3 / §7.5） |
| 门到门时间靠感觉 | **确定性门到门计算**（§9.1），不靠模型 |
| 估算值伪装成确定值 | **六态信息体系 + 前端渲染铁律**：估算与确认永远长得不一样（§6.1） |

> **对我们的启发**：通用大模型是最好的**反面教材**。它证明了 PRD"证据优先"和技术方案"防幻觉护栏必须是架构级强约束、而非提示词请求"的判断是对的。**我们的差异化不是'模型更强'，而是'我们知道模型会错，并用工程把错误关在笼子里'。**

## 5. 国际 AI 旅行规划产品

> 国际产品对我们主要是**交互与前端表达**的参考；其后端多为闭源，技术判断以公开描述 + 行为推断为主。它们普遍面向**境外长途**场景，弱在**跨城交通门到门**与**多人协同**——这正是我们的机会点。

### 5.1 Mindtrip——LLM + POI 库 + 交互式地图 + RAG grounding

- 定位"AI-powered travel, personalized to you"，强调 photos/reviews/maps。
- **技术推断**：典型的 **LLM + 结构化 POI 知识库 + 地图**架构，用 **RAG grounding**（检索真实 POI/评价注入 prompt）抑制幻觉，前端强在**交互式地图 + 卡片式 POI**。
- 强项：目的地灵感、可视化行程；弱项：跨城交通决策、实时票务、多人约束。

### 5.2 Layla（前身 Roam Around）——chat-first 全流程助手

- 定位 chat-first AI trip planner，宣称能 plan/book/manage flights + hotels + road trips。
- **技术推断**：对话式编排 + 接入航班/酒店比价 API + 预订跳转。相比国内 OTA，Layla 更像"对话式聚合 + 部分代订"。
- 与我们的差异：Layla **走向代订**（触碰交易），我们**明确不碰**。

### 5.3 Wanderlog——协作式行程管理（偏工具，弱 AI）

- 免费行程规划器，强在**多人协作、行程表、地图、预订归集**于一体。
- **技术推断**：以**结构化行程数据模型 + 协作（实时同步）+ 地图**为核心，AI 是辅助而非主体。
- **对我们的启发**：其"**一个 app 管理一次旅行的所有环节 + 多人协作**"的产品形态，与我们的 Trip Bundle + 多人聚合有共鸣。它的协作数据模型（谁能看/改哪些字段）值得参考——尽管我们更强调隐私（默认只展示聚合结果）。

### 5.4 TripIt——"回填/BYO Booking"的鼻祖，最值得深挖的解析引擎

**TripIt 是本产品"你的订单即数据"原则最直接的先行者**，其核心技术就是我们回填功能要做的事。

**技术架构（多格式预订解析引擎）：**

```text
用户转发预订邮件到 plans@tripit.com（或授权 Gmail 自动导入）
        │
        ▼
┌─────────────────────────────────────────────┐
│  邮件摄取层：识别发件人身份、路由到解析器          │
├─────────────────────────────────────────────┤
│  解析层：数千种预订格式的解析器                    │
│  （航司确认信/酒店/租车/餐厅…规则模板 + ML + 近年 LLM）│
├─────────────────────────────────────────────┤
│  结构化层：抽取航班号/发到时间/酒店/确认号          │
│  → 合并成统一 Master Itinerary（按时间线排序）      │
└─────────────────────────────────────────────┘
```

- TripIt 解析"数千种"预订邮件格式（航司/酒店/租车/餐厅），近年结合 **Apple Intelligence** 把邮件/照片/PDF 转成结构化行程。
- 本质是**"格式极其碎片化、无统一 API"场景下的抽取工程**——与国内"12306/活动无开放 API"的困境同构。

> **对我们的启发（关键）**：
> - TripIt 证明了**"用户已有预订 → 结构化 → 汇入统一行程"是被验证 15+ 年的刚需**，我们的"回填（文本/截图/链接）"就是它的现代 LLM 版本。
> - 差异与升级：TripIt 靠**规则模板矩阵**（维护成本高、格式一变就挂），我们用 **Qwen-OCR + 小模型抽取 + Function Calling schema**，对新格式泛化更好；且我们**强制用户逐字段确认**（confirmed_by_user），比 TripIt 的"自动导入"更符合"证据优先"。
> - 可借鉴：TripIt 的**"统一 Master Itinerary 时间线合并"**数据模型，正是我们 `TimelineSolver` 要产出的东西。

## 6. 横向技术模式总结

把所有对手的技术选择抽象成可对比的维度：

| 维度 | 国内 OTA（飞猪/携程/同程） | 内容生态（马蜂窝/小红书） | 通用大模型（豆包等） | 国际（Mindtrip/Layla/TripIt） | **周末去哪儿** |
|---|---|---|---|---|---|
| **编排范式** | 多智能体 / 智能体直连数据池 | 双模型 / 生成+质检 | 单模型 + 联网搜索 | 对话式编排 / 解析引擎 | **显式状态机（LangGraph）+ 两段式中断** |
| **数据来源** | 自家实时库存（可下单） | 自家 UGC 知识图谱 | 联网搜索（无约束） | POI 库 / 用户预订 | **官方来源证据库 + 用户回填 + 确定性服务** |
| **抑制幻觉** | 垂类数据/可靠答案库 | 第二模型交叉验证 | 基本无（靠模型自觉） | RAG grounding | **架构级 Provenance Guard + 六态证据** |
| **交易** | ✅ 一键下单（核心） | 部分 / 跳转 | ❌ | 部分代订 | **❌ 刻意不做（护城河）** |
| **交通决策** | 比价卡（卖票导向） | 弱 | 编造风险高 | 弱（偏境外） | **门到门确定性计算（中立）** |
| **多人协同** | 弱 | 弱 | 无 | Wanderlog 有协作 | **匿名邀请 + 聚合 + 公平性（隐私优先）** |
| **人在环** | 隐式（对话确认） | AI 路书主动提问 | 无 | Layla 对话确认 | **interrupt 一等公民（等回填跨天恢复）** |
| **成本结构** | 重（自研模型+库存） | 重（内容+双模型） | 中 | 中 | **轻（分层 LLM + 缓存 + 免训练）** |

**三个跨产品共识（被反复验证的价值点）：**

1. **实时/可信数据 + 编排 = 价值核心**（评测分差、飞猪第一都证明）。我们用"证据库 + 确定性服务"替代"实时库存"。
2. **抑制幻觉是旅游 AI 的生死线**（马蜂窝"最不能容忍幻觉"、通用模型翻车）。我们把它做成架构级护栏 + 硬 KPI。
3. **先主动澄清需求，再规划**（马蜂窝 AI 路书、飞猪行程助手先分析需求）。我们的 ConstraintParser 追问机制方向正确。

**一个集体空位（我们的机会）：**

> 所有人都在"卖库存/卖内容/卖生成"，**没有人做中立的、跨平台的、证据透明的决策层**。原因是商业模式冲突（OTA 靠佣金、内容平台靠流量）。这个空位不是别人做不到，而是**别人不愿做**——这才是可持续的护城河。

## 7. 对标「周末去哪儿」

### 7.1 我们已经做对的（被竞品验证）

| 我们的设计 | 被谁验证 | 结论 |
|---|---|---|
| 证据优先 / 防幻觉护栏 | 马蜂窝双模型质检、通用模型翻车 | ✅ 方向正确，且我们的实现更轻 |
| 显式状态机 + 人在环 | 飞猪/程心的编排、马蜂窝主动提问 | ✅ 编排是共识，我们的"可中断/可回退"更强 |
| 约束收集先追问 | 马蜂窝 AI 路书"先主动提问" | ✅ 交互模式已被市场验证 |
| 读写解耦（规划流 vs 情报流） | 同程"Agent 直连数据池" | ✅ 工程解耦是共识 |
| 结构化卡片表达 | 飞猪比价卡/对比表、Mindtrip 地图卡 | ✅ 应加强前端卡片化 |

### 7.2 我们刻意不做的（战略取舍，不是短板）

- **不做交易/实时库存**：飞猪/携程/同程的核心能力，我们主动放弃 → 换来中立性。**风险**：用户可能觉得"还要自己去买票"麻烦。**对策**：把回填做到极致顺滑（TripIt 级解析 + OCR）、起售提醒到点即点。
- **不自研垂直大模型**：携程 200 亿数据训练的路线我们玩不起，也没必要 → 用"窄场景 + 官方证据 + 分层通用 LLM"达到同等可信。
- **不绑内容生态**：马蜂窝/小红书的 UGC 护城河我们没有 → 我们的护城河是**跨平台整合 + 证据透明 + 城市档案运营**。

### 7.3 可直接借鉴、应纳入迭代的（高优先级）

1. **【交互】马蜂窝 AI 路书式"选择题补全需求"**：作为 ConstraintParser 的 UX 基线，降低"填表焦虑"。
2. **【前端】飞猪式结构化对比卡**：城市卡/交通卡加"三维对比表 + 动线图"，估算值与确认值视觉区分（呼应我们六态渲染铁律）。
3. **【交通】飞猪多目标优化 + 解释分离**：门到门计算用确定性优化，LLM 只做"为什么推荐这个时间窗"的解释——我们已有此设计，应确保 LLM 绝不参与数值计算。
4. **【回填】TripIt 统一时间线合并模型**：把回填的车次/航班/酒店合并成 Master Timeline 的数据结构，直接指导 `TimelineSolver`。
5. **【质检】马蜂窝"质检员"思想的轻量化**：我们不加第二个模型，但可在 `FeasibilityValidator` 后加一道**"证据完备度质检"**（关键字段是否都有 source/status），作为出稿前的最后一关。

### 7.4 需要警惕的竞争风险

- **大厂下沉到"周末近途"场景**：飞猪/携程若推出"周末去哪儿"式功能，凭实时库存可快速覆盖。**我们的防御**：① 中立性（他们无法放弃佣金）；② 深耕 15–20 城的活动情报运营（脏活、护城河）；③ 多人隐私协同（大厂受制于生态账户体系）。
- **通用 Agent 平台（支付宝/夸克/Manus 类）聚合**：可能把我们的功能当成一个"技能"聚合。**防御**：把"当周活动证据库 + 城市档案"做成难以复制的数据资产。

## 8. 结论

1. **赛道已被验证，空位真实存在**：头部产品用"实时数据 + 编排 + 抑制幻觉"赢得市场，但全部绑定交易、推荐向库存倾斜。**中立决策层是被集体让出的结构性空位**。
2. **我们的技术路线经得起竞品拷问**：证据优先、显式状态机、读写解耦、先追问后规划——每一条都能在头部产品身上找到验证，且我们的实现**更轻、更适合小团队**。
3. **最大的技术赌注是对的**：把"防幻觉"做成架构级护栏（而非提示词），是从通用大模型翻车和马蜂窝"双模型质检"两个方向共同验证的正确决策。
4. **最该补强的三件事**：① 回填体验（向 TripIt 看齐）；② 前端结构化卡片（向飞猪看齐）；③ 约束收集交互（向马蜂窝 AI 路书看齐）。
5. **护城河的本质不是技术，是"别人不愿做的脏活 + 别人不能放弃的商业模式冲突"**：城市活动情报运营 + 中立性，这两点大厂"做得到但不愿做"，才是可持续壁垒。
