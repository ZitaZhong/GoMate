## 1. 执行摘要

**三个核心判断：**

1. **本产品选型（LangGraph + interrupt + Postgres checkpoint）已被开源社区充分验证。** 其中 `RoamWise` 几乎是本产品的开源"平行实现"——同样用 LangGraph 编排、同样在每个关键步骤 `interrupt` 等待人工确认、同样持久化会话可跨天恢复、同样坚持**"没有用户明确确认就不自动下单"**。这不是巧合，而是"可信旅行 Agent"这一问题域的**收敛解**。

2. **绝大多数开源项目的致命短板，恰是我们的设计重点。** 它们几乎无一例外地：**把 SerpAPI/搜索结果直接当事实**（无来源、无状态、无过期），**无门到门确定性计算**（时间靠 LLM 编），**无证据体系**。它们能做出"看起来能跑的 demo"，但一旦上真实交通/票价就会翻车——这正是通用大模型翻车的同一个坑。**我们的 Provenance Guard + 六态证据 + 确定性服务，是把 demo 变成产品的关键分界线。**

3. **两种编排范式的选择已有定论。** `LangGraph`（显式状态图 + 中断 + 检查点）适合**长周期、可中断、需回退、人在环**的工作流——正是我们要的；`CrewAI`（角色制、agent 自由协作）适合**一次性、无需中断**的快速生成，不适合我们的两段式。**开源证据支持我们选 LangGraph。**

## 2. 开源旅行 Agent 全景

### 2.1 按"编排范式"分类

```text
① ReAct 单体循环         LLM ⇄ tools 循环，直到无 tool_call 才结束
   代表：nirbar1985       适合：简单查询类；不适合多阶段规划

② 并行扇出 + 合并         多个独立节点并行跑，用 reducer 合并状态
   代表：sergio11         适合：互不依赖的信息采集（航班/酒店/活动并行）

③ 顺序状态机 + 人在环     节点按依赖顺序执行，关键点 interrupt 等确认
   代表：RoamWise ⭐       适合：我们的两段式规划（探索→确认）

④ 角色制 Crew            多个"角色 agent"协作，框架调度
   代表：CrewAI 系列       适合：一次性生成，不需中断/回退

⑤ Plan-and-Solve 研究     planner 拆问题→executor 检索→publisher 汇总带引用
   代表：gpt-researcher ⭐ 适合：我们的"当周活动即时调研 + 证据"
```

> **本产品是 ③ + ⑤ 的融合**：主干是"顺序状态机 + 人在环"（③，像 RoamWise），其中"活动情报流水线"是"Plan-and-Solve 证据研究"（⑤，像 gpt-researcher），局部信息采集可用"并行扇出"（②）。

### 2.2 一个残酷的共性：都没有"证据"和"确定性交通"

| 项目 | 交通数据来源 | 有来源标注? | 有过期? | 有门到门计算? | 有人在环? |
|---|---|---|---|---|---|
| nirbar1985 | SerpAPI Google Flights | ❌ | ❌ | ❌ | ✅(发邮件前) |
| vikrambhat2 | 无(LLM 编) | ❌ | ❌ | ❌ | ❌ |
| sergio11 | Tavily 搜索 | ❌ | ❌ | ❌ | ❌ |
| CrewAI 系列 | SerpAPI | ❌ | ❌ | ❌ | ❌ |
| RoamWise | 自定义搜索工具 | 部分 | ❌ | ❌ | ✅(每步) |
| **周末去哪儿** | **官方源+回填+VariFlight** | **✅六态** | **✅expires_at** | **✅确定性** | **✅interrupt** |

> **这张表就是我们的差异化清单。** 开源项目擅长"把 LLM 和工具接起来"，但没有一个解决"可信"——因为可信是**产品级投入**（证据运营 + 确定性工程），不是**技术 demo** 能顺带做出来的。

## 3. LangGraph 范式深度拆解

### 3.1 `nirbar1985/ai-travel-agent`——人在环中断的最小可用范本

**这是理解"interrupt 人在环"最干净的代码样本**（虽然它的场景是"发邮件前确认"，但机制与我们"回填前中断"完全一致）。

**① 状态定义：经典 messages 累加模式**

```python
from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage
import operator

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], operator.add]  # operator.add = 追加而非覆盖
```

> `Annotated[list, operator.add]` 是 LangGraph 的 **reducer** 机制：多个节点返回 `messages` 时自动**追加合并**而非覆盖。这是我们 `TripPlanState` 里 `warnings`、`activities` 等列表字段应该用的写法。

**② 图构建：ReAct 循环 + 条件边 + 中断**

```python
class Agent:
    def __init__(self):
        self._tools = {t.name: t for t in TOOLS}
        self._tools_llm = ChatOpenAI(model='gpt-4o').bind_tools(TOOLS)  # 工具绑定

        builder = StateGraph(AgentState)
        builder.add_node('call_tools_llm', self.call_tools_llm)
        builder.add_node('invoke_tools', self.invoke_tools)
        builder.add_node('email_sender', self.email_sender)
        builder.set_entry_point('call_tools_llm')

        # 条件边：LLM 还想调工具就去 invoke_tools，否则去 email_sender
        builder.add_conditional_edges('call_tools_llm', Agent.exists_action,
                                      {'more_tools': 'invoke_tools', 'email_sender': 'email_sender'})
        builder.add_edge('invoke_tools', 'call_tools_llm')  # 工具跑完回到 LLM（ReAct 循环）
        builder.add_edge('email_sender', END)

        memory = MemorySaver()
        # ★ 关键：发邮件前中断，等人确认
        self.graph = builder.compile(checkpointer=memory, interrupt_before=['email_sender'])

    @staticmethod
    def exists_action(state):
        return 'email_sender' if len(state['messages'][-1].tool_calls) == 0 else 'more_tools'
```

**③ 恢复执行：resume 不重跑前序节点**

```python
# app.py —— 用户点"确认发送"后：
config = {'configurable': {'thread_id': thread_id}}
st.session_state.agent.graph.invoke(None, config=config)  # 传 None = 从中断点继续
```

**关键洞察与映射：**

| nirbar1985 机制 | 「周末去哪儿」对应 | 说明 |
|---|---|---|
| `interrupt_before=['email_sender']` | `await_booking_node` 里的 `interrupt()` | 都是"执行敏感动作前停下等人" |
| `MemorySaver()` | **PostgresSaver**（我们要落库跨天） | MemorySaver 重启即丢，**生产必须换 Postgres** |
| `graph.invoke(None, config)` 恢复 | `graph.invoke(Command(resume=bookings), config)` | 新版 API 用 `Command(resume=...)` 传回填数据 |
| `thread_id` 关联会话 | `plan_id` 作 thread_id | 一个计划一条 checkpoint 线 |

> **可直接复用的模式**：ReAct 循环（`call_tools_llm ⇄ invoke_tools`）适合我们的 **`ActivityResearch` 节点**——LLM 决定"要不要再搜一个官方源"，搜完回到 LLM 判断信息是否够。但**主干规划流不用 ReAct**（太发散），而用固定顺序状态机。

**④ 工具封装：Pydantic schema + `@tool`（值得学的规范）**

```python
class FlightsInput(BaseModel):
    departure_airport: Optional[str] = Field(description='Departure airport code (IATA)')
    outbound_date: Optional[str] = Field(description='格式 YYYY-MM-DD, e.g. 2024-06-22')
    adults: Optional[int] = Field(1, description='成人数, 默认1')

@tool(args_schema=FlightsInputSchema)
def flights_finder(params: FlightsInput):
    '''Find flights using the Google Flights engine.'''
    params = {'api_key': os.environ.get('SERPAPI_API_KEY'),
              'engine': 'google_flights', 'departure_id': params.departure_airport, ...}
    search = serpapi.search(params)
    return search.data['best_flights']
```

> **这段代码同时是正面和反面教材：**
> - ✅ **正面**：`@tool + Pydantic args_schema + Field(description=...)` 是让 LLM 正确填参的标准做法，我们的**回填抽取工具、活动抽取工具**都该这样定义 schema（技术方案 §7.4 的 `EXTRACT_ACTIVITY_TOOL` 正是此模式）。
> - ❌ **反面**：`return search.data['best_flights']` **直接把 SerpAPI 结果当事实返回**，无来源、无 fetched_at、无 verification_status。如果这是车次/票价，就是"第一批 AI 旅游受害者"的成因。**我们的工具返回必须包一层 `Fact(value=..., evidence=Evidence(...))`。**

### 3.2 `vikrambhat2/MultiAgents-...`——"伪多智能体"反面教材

这个项目号称"MultiAgents"，但读代码会发现**它的"图"几乎是摆设**：

```python
workflow = StateGraph(GraphState)
workflow.add_node("generate_itinerary", generate_itinerary.generate_itinerary)
workflow.add_node("recommend_activities", recommend_activities.recommend_activities)
workflow.add_node("weather_forecaster", weather_forecaster.weather_forecaster)
# ... 7 个节点
workflow.set_entry_point("generate_itinerary")
workflow.add_edge("generate_itinerary", END)   # ← 每个节点都直接 →END
workflow.add_edge("recommend_activities", END)  # ← 节点之间没有依赖边！
workflow.add_edge("weather_forecaster", END)
# ...
graph = workflow.compile()
```

**问题诊断：**

- 7 个节点**全部直连 END**，节点间**没有数据依赖边**。入口只跑 `generate_itinerary`，其余节点**根本不在图的执行路径里**——它们实际是被 Streamlit 按钮**逐个手动调用**的独立 LLM 函数：

```python
if st.button("Get Weather Forecast"):
    result = weather_forecaster.weather_forecaster(st.session_state.state)  # 绕过图，直接调
```

> **教训（对我们极其重要）**：**"把函数命名为 agent、把它 add_node 进图" ≠ "多智能体编排"。** 真正的编排价值在于**节点间的依赖、状态传递、条件路由、中断恢复**。这个项目退化成"7 个互不相关的 LLM 调用 + 按钮"，图带来的持久化/回退/中断全部没用上。
>
> **我们必须避免的陷阱**：`TransportStrategy` 的输出必须真正**流入** `HotelAreaPlanning`（住宿区域依赖返程枢纽），`Timeline` 必须依赖 `bookings`——这些**依赖边**才是状态机的价值。如果我们的节点也都能"独立按钮触发"，说明编排设计失败了。

### 3.3 `sergio11/langgraph_travel_planner`——并行扇出 + reducer

**架构要点**（来自其 README 与代码结构）：

```text
TravelPlannerState（集中式状态）
   │
   ├─► [并行] flights 搜索节点 ┐
   ├─► [并行] hotels 搜索节点  ├─ 同时执行
   ├─► [并行] activities 节点  ┘
   │        （各自写回 state 的不同字段）
   ▼
自定义 Reducers 安全合并并发更新
   ▼
LLM 节点生成报告
```

- 栈：Python 3.11 + LangGraph + **ChatGroq(llama-3.3-70b)** + **Tavily**(实时搜索) + Gradio + Pydantic。
- 核心技术点：**"Custom Reducers to merge concurrent state updates safely during parallel execution"**——并行节点同时写状态时，用 reducer 避免竞争覆盖。

> **对我们的启发**：探索阶段的信息采集（多个城市的当周活动、多个交通方式的门到门估算）**天然可并行**。LangGraph 的并行扇出 + reducer 能显著降低探索版的响应延迟。但要注意：**并行的是"确定性计算/已就绪数据的读取"，不是"实时抓取"**（技术方案 §4.2 明确规划流不做实时抓取）。

### 3.4 `RoamWise`（sumanentc/travel-planner）——最接近的完整对标 ⭐

**这是整个开源调研中最有价值的项目**，它几乎是「周末去哪儿」的开源平行实现。

**依赖栈（注意版本，全是 2025 最新）：**

```text
langgraph==1.0.3      langchain==1.0.8      langchain-openai==1.0.3
chainlit==2.9.1       gpt-researcher==0.14.5    deepagents==0.2.8
```

**Agentic 工作流 + 人在环（README 明确的节点序列）：**

```text
用户查询
   ▼
[1] Validator Agent      分类意图（travel/闲聊/越界）+ 处理追问
   ▼
[2] Query Analyzer       抽取 query 类型、trip 类型、trip 目的
   ▼
[3] Entity Identifier    收集校验必要实体（目的地/日期/预算…）
   ▼  ★ Human Approval —— 用户确认或修改所收集的信息
[4] Transport Agent      交通推荐
   ▼  ★ Human Approval —— 用户审核批准交通建议
[5] Itinerary Planner    生成完整行程
   ▼  ★ Human Approval —— 用户审核/修改/批准最终行程
```

**项目结构（几乎能直接映射我们的目录）：**

```text
travel-planner/
├── workflow.py            # LangGraph 图定义   ←→ 我们的 build_graph()
├── agents/
│   ├── validator.py       # 意图分类
│   ├── query_analyzer.py  # 查询分析
│   ├── entity_identifier.py  ←→ 我们的 ConstraintParser
│   ├── transport.py          ←→ 我们的 TransportStrategy
│   ├── accomodation.py       ←→ 我们的 HotelAreaPlanning
│   ├── itinerary.py          ←→ 我们的 TimelineSolver/PlanComposer
│   ├── decision.py        # 决策路由（条件边逻辑）
│   └── prompts.py         # ★ 所有 system prompt 集中管理
├── models/agent_models.py # Pydantic 数据模型  ←→ 我们的 Fact/Evidence/Booking
└── tools/custom_tools.py  # web 搜索/交通/住宿工具
```

**四条与我们高度一致的设计决策：**

| RoamWise 设计 | 「周末去哪儿」对应 | 一致性 |
|---|---|---|
| 每个关键步骤 `interrupt` 等人工批准 | 两段式 `interrupt()` 等回填 | ★★★ 核心机制完全一致 |
| **"No automated bookings without explicit confirmation"** | **不做交易 + 回填确认后才生效** | ★★★ 产品哲学完全一致 |
| SQLite 持久化聊天历史、可恢复会话 | PostgresSaver checkpoint 跨天恢复 | ★★★ 思路一致（我们更强，用 Postgres） |
| prompts 集中管理、Pydantic 模型 | 提示词纪律 §7.5 + Fact/Evidence 模型 | ★★★ 工程规范一致 |
| Validator 先分类意图/处理追问 | ConstraintParser 追问补全 | ★★ 交互一致 |

**RoamWise 缺失、而我们必须补上的（我们的护城河）：**

1. **无证据体系**：它的交通/住宿来自搜索工具，无 source/status/过期。→ 我们有六态证据 + Provenance Guard。
2. **无门到门确定性计算**：Transport Agent 是 LLM 生成建议。→ 我们有 `door_to_door()` 确定性计算。
3. **无多人协同/隐私聚合**：单用户。→ 我们有匿名邀请 + 聚合 + 公平性。
4. **无起售提醒/ICS/天气重规划**：无提醒系统。→ 我们有完整提醒与重规划触发器。

> **结论**：RoamWise **验证了我们主干编排（LangGraph + 每步 HITL + 持久化）是成熟、可落地的**；而我们相对它的**全部增量（证据、确定性交通、多人、提醒、重规划）恰恰就是"从开源 demo 到可信产品"的距离**。**可以把 RoamWise 当作我们 v0.1 主干的参考实现来读，但绝不能止步于它的可信度水平。**

## 4. CrewAI 范式

### 4.1 `arjunprabhulal/gemini-crewai-travelplanner`——角色制多智能体

**架构（CrewAI 的"角色-任务"模型）：**

```text
Gemini 2.0 LLM  +  CrewAI 编排  +  SerpAPI(实时机酒)  +  FastAPI + Streamlit

三个角色 Agent（各有 role/goal/backstory）：
  ① Flight Analyst Agent  —— 按价格/时长/中转分析航班，给结构化推荐 + 理由
  ② Hotel Analyst Agent   —— 按价格/评分/位置/设施评估酒店，给优缺点
  ③ Travel Planner Agent  —— 用航班+酒店信息生成逐日行程

CrewAI 以 Process（sequential/hierarchical）调度这些 agent 协作
数据用 Pydantic models 校验
```

**CrewAI vs LangGraph（为什么我们选 LangGraph）：**

| 维度 | CrewAI（角色制） | LangGraph（状态图） | 我们的需求 |
|---|---|---|---|
| 编排单位 | Agent 角色 + Task | Node + Edge + State | — |
| 控制流 | 框架隐式调度（agent 自主） | **显式图，每步可见** | ✅ 需要显式可见 |
| 中断/人在环 | 弱（需自研胶水） | **`interrupt()` 原生** | ✅ 两段式必需 |
| 可回退 | 弱 | **checkpoint 历史 + update_state** | ✅ "每步可回退"必需 |
| 持久化跨天 | 需自建 | **Checkpointer 原生** | ✅ 等回填跨天必需 |
| 上手速度 | 快（写角色即可） | 中（要设计状态/边） | — |
| 适合场景 | 一次性生成攻略 | **长周期可中断工作流** | ✅ 我们是后者 |

> **结论**：CrewAI 适合"输入需求→一口气生成一份攻略"的**一次性**场景（正是这个 demo 做的）。但我们的产品是**"探索→离开去买票→几天后回来→确认"**的长周期、可中断流程，CrewAI 的隐式调度和弱中断/弱回退**无法满足**。技术方案 §3.1 选 LangGraph 的判断，在开源对比中站得住。

## 5. 证据研究范式：GPT-Researcher

**28.5k★ 的明星项目，是我们"当周即研 + 证据优先"最直接的技术原型。**

**架构（Plan-and-Solve + RAG，灵感来自 STORM 论文）：**

```text
研究查询
   ▼
Planner Agent      生成一组研究问题（拆解 objective）
   ▼
Execution Agents   为每个问题派 crawler agent 检索（可并行）
   ▼
每个资源：Summarize + Source-track（★ 摘要 + 来源追踪）
   ▼
Filter & Aggregate 过滤聚合成最终报告（带 inline citations）
   ▼
Publisher          输出 PDF/Docx/Markdown，含引用
```

**它抑制幻觉的方法论（README 原话）：**

> "By scraping multiple sites per research, and choosing the most frequent information, the chances that they are all wrong is extremely low." —— **多来源交叉 + 取高频事实**降低错误率。

**关键工程能力：**

- **Source-track each resource**：每条信息都追踪来源——**这就是我们 `Evidence.source_url / fetched_at` 的开源实现证明**。
- **20+ 来源聚合**、**保持研究上下文记忆**。
- **多智能体版**用 **LangGraph + AG2** 构建；支持 **MCP** 接入 GitHub/DB/自定义 API 作为数据源。
- 已被封装为 **Claude Skill** 与 **MCP Server**。

**映射到我们的"活动情报流水线"（技术方案 §8）：**

| GPT-Researcher | 「周末去哪儿」活动情报流水线 | 说明 |
|---|---|---|
| Planner 生成研究问题 | 来源注册表 + "城市×本周末×品类"检索策略 | 我们的"问题"是结构化的城市+品类 |
| Crawler 检索每个问题 | Fetcher（httpx/Playwright）抓官方源 | 我们**只抓白名单官方源**，更克制 |
| Summarize + **Source-track** | LLM `emit_activity` + **evidence_quote** | 我们强制"指出出处原文片段" |
| 多来源取高频 | 去重 + 实体对齐（pgvector）+ 官方源覆盖搜索源 | 我们**按可信度定级**而非取高频 |
| inline citations | verification_status + source_url 渲染 | 我们把引用变成 UI 状态角标 |

> **两点关键差异（我们更严格）：**
> 1. GPT-Researcher **"取高频"** 来降噪；我们**"按来源可信度定级"**（官方源 > 搜索源），因为旅行事实（营业时间/活动时间）**"高频"不等于"正确"**，只有**官方**才算数。
> 2. GPT-Researcher 面向"生成研究报告"（可容忍少量偏差）；我们面向"可执行行程"（车次/票价**零容忍编造**）。所以我们在它之上加了 **Provenance Guard 硬闸 + 字段级来源白名单**。
>
> **可直接复用**：`gpt-researcher` 已是 pip 包（RoamWise 就把它作为依赖 `gpt-researcher==0.14.5`）。我们的**活动情报流水线可以直接集成 gpt-researcher 做"找官方入口"的检索层**，但**事实抽取与定级必须走我们自己的证据管线**，不能直接用它的报告输出当事实。

## 6. 底层关键技术

### 6.1 LangGraph interrupt / checkpoint / HITL（我们的技术命门）

综合 LangChain 官方文档与上述项目代码，HITL 的**四要素**：

```text
① Checkpointer 配置    —— 没有 checkpointer 就没有 interrupt（状态无处保存）
② interrupt() 调用     —— 在节点内暂停，把控制权交回外部
③ thread_id 关联       —— config={'configurable':{'thread_id': plan_id}}
④ Command(resume=...)  —— 恢复时把人工输入传回，★ 不重跑前序节点
```

**官方文档关键点（对我们的保证）：**

- **"interrupt 使用 LangGraph 的持久化层保存状态，可无限期暂停，直到你恢复"**——这正是我们"用户去 12306 买票，几小时/几天后回来继续"所需。
- **恢复只从中断点继续，不重新执行前序节点**（Reddit/Medium 多方印证）——保证探索版的前 4 步不会因回填而重算，省钱省时。

**新旧 API 对照（编码要注意）：**

```python
# 旧写法（nirbar1985 用的）：编译期声明中断点
graph = builder.compile(checkpointer=saver, interrupt_before=['await_booking'])
graph.invoke(None, config)  # 恢复：传 None

# 新写法（LangGraph 1.0 推荐，我们的技术方案 §5.2 用的）：节点内动态中断
def await_booking_node(state):
    user_bookings = interrupt({"type": "await_booking", "explore_bundle": ...})
    return {"bookings": user_bookings, "stage": "confirm"}
graph.invoke(Command(resume=confirmed_bookings), config)  # 恢复：传回填数据
```

> **落地提醒**：MVP 千万别用 `MemorySaver()`（进程重启即丢，nirbar1985 就是这个问题）。**直接上 `PostgresSaver`**（技术方案已定），并给 checkpoint 设 **TTL/归档策略**（§14 风险登记册"长周期 interrupt 状态膨胀"）。

### 6.2 三种持久化后端对比

| 后端 | 项目实例 | 特点 | 适用 |
|---|---|---|---|
| MemorySaver | nirbar1985 | 内存、重启即丢 | 仅 demo/测试 |
| SQLite | RoamWise | 单机文件、可跨会话 | 小型/单机部署 |
| **PostgresSaver** | **周末去哪儿** | 关系库、可水平扩展、事务 | ✅ **生产（我们的选择）** |

> RoamWise 用 SQLite 已能实现"会话恢复"；我们用 Postgres 是因为要**同时承载业务数据（活动/证据/PostGIS/pgvector）+ checkpoint**，"一个 Postgres 打三份工"（技术方案 §3.4）。

## 7. 反面参照：12306 抢票开源

**为什么要研究抢票项目？** 因为它们代表了**我们主动拒绝的那条路**——直接对接/爬取交易平台。读懂它们的困境，才能理解"不做交易 + 回填"为何是唯一正确解。

**代表项目：`testerSunshine/12306`、`py12306`**（GitHub 抢票热榜前二）

**它们的技术栈与困境：**

```text
爬虫（模拟 12306 接口） + 验证码识别（TensorFlow/keras/sklearn 训练模型或调打码平台）
   + 分布式抢票 + 候补捡漏 + Cookie 身份维持 + 邮件通知
        │
        ▼ 现实困境（多方实测/文章印证）：
   ① 验证码策略一变，热榜第一/第二的项目集体"挂掉"
   ② 需要用户名密码/Cookie —— 触碰账户与个人信息，合规红线
   ③ 12306 官方多次声明"从未授权任何第三方发售火车票"
   ④ 接口随时变更，稳定性极差，靠社区"复活教程"续命
```

**这四条困境，逐条印证了我们的设计（技术方案 §2.1）：**

| 抢票项目的困境 | 「周末去哪儿」的规避设计 |
|---|---|
| ① 验证码/接口一变就挂 | **不碰接口**：策略卡 + 起售时间是**规则计算**，不依赖实时接口，永不失效 |
| ② 需账户/Cookie，合规红线 | **不代登录、不代购、不读密码**（§12），从架构消除最大合规风险 |
| ③ 官方声明未授权第三方 | **深链跳官方 + 用户自行在官方完成交易**，我们只做决策层 |
| ④ 稳定性差靠复活教程 | **回填**（文本/截图/链接）稳定可控，不受官方接口波动影响 |

> **深刻结论**：抢票项目再"聪明"，也建立在**与官方对抗**的地基上——注定不稳定、不合规、不可持续。**我们的"不做交易 + 回填 + 起售提醒"不是能力缺失，而是把地基从"对抗官方"换成了"协作官方"。** 这是本产品最反直觉、也最正确的架构决策，开源抢票项目的集体困境就是最好的证明。

## 9. 对标「周末去哪儿」：落地代码骨架

综合上述所有开源实现的**正确模式**，给出可直接开工的骨架建议（与技术方案 §5.2 对齐并强化）：

### 9.1 状态定义：列表字段全部配 reducer（学 nirbar1985）

```python
from typing import Annotated, TypedDict, Literal
import operator

class TripPlanState(TypedDict):
    plan_id: str
    stage: Literal["explore", "await_booking", "confirm"]
    constraints: dict
    party: list[dict]
    candidate_cities: list[dict]
    activities: Annotated[list[dict], operator.add]   # ★并行研究时追加合并
    transport_options: dict
    bookings: list[dict]
    # ...
    warnings: Annotated[list[str], operator.add]      # ★多节点都可能追加告警
```

### 9.2 依赖边必须"真连"（避免 vikrambhat2 陷阱）

```python
# ★ 反例（vikrambhat2）：节点全部 →END，图形同虚设
# g.add_edge("hotel", END); g.add_edge("dining", END)  # ← 禁止！

# ★ 正例：让数据真正在节点间流动（住宿依赖返程枢纽，时间线依赖回填）
for a, b in [("transport","await_booking"),   # 交通策略 → 中断等回填
             ("await_booking","hotel"),         # 回填 → 住宿区域（依赖返程枢纽）
             ("hotel","mobility"),("mobility","dining"),
             ("dining","timeline"),             # 时间线依赖 bookings + dining
             ("timeline","validate"),("validate","compose")]:
    g.add_edge(a, b)
```

### 9.3 工具返回必须包证据（补齐所有开源的短板）

```python
# ★ 开源通病（nirbar1985/CrewAI）：return serpapi_result  ← 无来源，禁止
# ★ 我们的铁律：任何对用户展示的事实都包成 Fact
def flight_schedule_tool(...) -> Fact:
    raw = variflight_api.query(...)          # 付费航班时刻（可信来源）
    return Fact(value=raw, evidence=Evidence(
        source_type="variflight",
        source_url=..., fetched_at=now(),
        verification_status=VerificationStatus.public_source_observed))
# 交通"实时票价/余票"字段：LLM 与搜索都不在白名单 → 强制降级为"待官方确认"
```

### 9.4 中断节点：先出探索版，再等回填（学 RoamWise 的每步确认 + 我们的两段式）

```python
def await_booking_node(state: TripPlanState):
    explore_bundle = compose_explore_bundle(state)      # 先产出可分享的探索版
    user_bookings = interrupt({                          # 持久化并交还控制权
        "type": "await_booking",
        "explore_bundle": explore_bundle,
        "prefill": build_prefill_hints(state["transport_options"]),  # 预填清单
    })
    return {"bookings": user_bookings, "stage": "confirm"}
# 恢复：graph.invoke(Command(resume=confirmed_bookings), config={"configurable":{"thread_id": plan_id}})
```

### 9.5 情报流水线：借 gpt-researcher 检索，走自己的定级

```python
# 检索层可复用 gpt-researcher（找官方入口）；抽取+定级必须自建
async def research_weekend_activities(city, weekend):
    entries = source_registry.enabled_sources(city)      # 白名单官方源
    for src in entries:
        if not robots_ok(src.entry_url): continue         # 合规硬闸
        page = await fetch_and_clean(src.entry_url)        # httpx/Playwright + Readability
        acts = await llm_extract(page, tool=EXTRACT_ACTIVITY_TOOL)  # 带 evidence_quote
        for a in acts:
            a = normalize(a); a = enforce_provenance(a, src)  # 定级：官方源→confirmed
            upsert_with_dedup(a)                              # fingerprint + pgvector 去重
```

## 10. 结论

1. **主干选型被开源充分背书**：`RoamWise` 用与我们几乎相同的技术栈（LangGraph 1.0 + 每步 HITL + 持久化 + "不自动下单"）跑通了完整流程。**我们的技术方案 §3.1/§5 不是纸上谈兵，而是有开源平行实现可对照的成熟路线。**

2. **所有开源项目的天花板恰是我们的起点**：它们把 LLM 和工具接起来就止步了，普遍缺**证据体系、确定性交通、防幻觉护栏、多人协同、提醒与重规划**。**"从 demo 到可信产品"的全部距离，就是我们的护城河清单。**

3. **两个可直接复用的开源资产**：① 主干编排参考 `RoamWise` 的目录与图结构；② 活动情报检索层可集成 `gpt-researcher`（pip 包），但**事实定级必须过我们自己的证据管线**。

4. **一个必须坚守的反面教训**：`vikrambhat2` 证明"命名为 agent ≠ 编排"，**节点依赖边才是状态机的价值**；`12306 抢票`项目证明"对抗官方"的地基注定不稳，**我们"协作官方 + 回填"的路线才可持续**。

5. **编码优先级建议**：先照 `RoamWise` 骨架把"LangGraph + interrupt + Postgres checkpoint"主干跑通（风险最低、有参照），再逐层叠加**证据体系 → 确定性门到门 → 情报流水线**这三块"开源无参照、但决定成败"的护城河代码。

> **与《01_竞品技术方案深度分析报告》合看**：竞品报告告诉我们**"做什么、不做什么"（中立决策层的战略空位）**；本报告告诉我们**"怎么用代码把它做出来、以及别人踩过的坑"**。两份报告共同支撑一个结论——**「周末去哪儿」的技术路线，在商业竞品和开源实现的双重坐标系里，都站得住脚。**
