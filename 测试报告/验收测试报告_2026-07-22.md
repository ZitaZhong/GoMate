## 一、总体结论

**不通过，不能交付用户。**

更准确的画像是：**"横向纪律"真实，"纵向决策智能"大多是桩。**

- 真实的部分：两段式状态机、证据六态与最终闸、Provider 无 key 降级链、混合检索管线、禁忌过滤、ICS 导出、活动情报流水线内核、扩展安全铁律。这些"不让系统说错话"的机制是真代码、有测试。
- 是桩的部分：PRD 卖给用户的核心价值——**跨城方式判断、门到门计算、查询策略卡、无票策略、当周活动调研、对话式规划、多人协作、天气感知、提醒投递**——要么未实现，要么实现了但没接线（死代码），要么写死数据冒充真实结果。

**特别警告（比"没做"更糟的三处）**：
1. **餐饮候选是 3 家写死的假餐厅**（"本帮菜馆"/"江浙小馆"/"稳妥快餐"），披着真实推荐的外衣（stay_mobility_dining.py:75-82）；
2. **市内接驳时长是 `20+i*5` 的等差数列**，从不调用地图（stay_mobility_dining.py:55）；
3. **门到门时间恒为 0**（"缺少坐标"），但 UI 仍展示"门到门约 0 分钟"——这些在界面上看起来都"像功能"，实际是假的。这违背 PRD 自己最强调的"诚实"KPI。

## 五、实测通过项（可保留的底子）

1. 两段式主闭环状态机（探索→interrupt→回填→确认），SSE 逐节点可见，revise 可回退；
2. 证据六态全字段落地 + 最终闸真拦截 + 交通禁编红线（CI 有红线测试）；

4. 混合检索（稠密+稀疏+RRF+可信源硬过滤）与忌讳过滤、稳妥备选；
5. 12306 官方入口与起售提醒规则计算（不越界代查余票）；
6. 回填→确认版组装（酒店/火车锚点入时间线，校验放行）；
7. 活动情报流水线内核（robots 遵守/归一化/两级去重/流水线定级）；
8. 扩展 MV3 合规与安全铁律（不读密码、不批量抓、确认后提交）；
9. Postgres checkpoint 持久化、plan_lock 串行、422 校验、空约束优雅兜底；
10. 自带测试 117/117 通过（但覆盖的是契约层，未覆盖本报告的端到端场景）。

## 六、验收意见

**不予放行。** 建议按三个批次修复：

**批次一（放行前置，估计 3-5 天）**
1. 修 `_same_city()` 硬编码（P0-1）；补 `decide_mode` 距离带判断（P1-1）；
2. 统一时区（活动存本地时间带时区或全部 UTC+前端转换）+ validate 回退加次数上限与 compose 逃生（P0-2、P1-4）；
3. 假数据三处要么接真源（高德 POI/route），要么在 UI 明确标注"示例数据"（P0-3）——按 PRD 自己的 KPI，假数据当真数据展示是不可接受的；
4. 补端到端回归用例：上海→杭州跨城、同城+latest_return、回填→确认版——现有 117 项测试一个都没覆盖这些。

**批次二（核心承诺，决定产品是不是"周末去哪儿"）**
5. 配 SEARCH/LLM key 并验证 DD-17 真实联网调研 + 文本粘贴抽取（P1-2、P1-6）；
6. 候选城市池出 3 卡（P1-3）；门到门接坐标、接驳段补全（§5.5-A）；
7. Copilot 最小闭环：约束抽取写入图 + ask_info 真回答 + 回填消息真触发（P1-9）；
8. redact() 接入 LLM 调用边界（P1-10，安全前置）。

**批次三（体验完整度）**
