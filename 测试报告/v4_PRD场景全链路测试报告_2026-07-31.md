## 一、结论摘要

以真实用户身份完成两次完整多轮规划会话（plan 4742 市内多人游、plan 4743 跨城一日游），覆盖 PRD 全部核心能力：多人集合决策、路途时长估算、完整路线+时段编排、地铁接驳、动线餐饮+忌口/预算、修改保留、证据诚实问答、跨城门到门交通策略、订单回填→确认版时间线、天气重规划、多人匿名邀请聚合、ICS 导出。

- **通过（PASS）：12 项**核心场景按 PRD 预期工作，含时间轴编排、段间地铁接驳耗时、动线餐饮约束、证据六态角标、来源可溯、日期冲突检测、门到门比较、回填确认版、多人公平聚合。
- **含瑕疵通过（PASS with caveat）：1 项**——S1 三个子任务（集合点/上午景点/路途时长）均有回应，但"推荐上午景点"仅落地一个且以"离集合点近"为主要理由，弱于"推荐（多个）适合一起逛的景点"的合理预期（详见 S1）。
- **发现并已修复缺陷：3 个**
  1. 【高】目的地澄清死循环——回答城市后仍反复追问（已修复 + 回归测试）
  2. 【中】订单回填 `kind=manual` 被拒 422——前端回填面板默认入口不可用（已修复 + 回归测试）
  3. 【已存在于展示层，未改动】禁止搜索本地重排时，用户口头指定但未成为候选卡的地点（武康路）被静默丢弃（根因已定位，作为发现上报）
- **回归**：全量 `uv run pytest` **354 passed**（既有 22 文件零修改 + v4 新增 4 文件，含本轮新增 2 个回归用例）。
- **PRD 硬 KPI（§11 可信度）实测**：`turn_silent_terminal_total=0`、`promised_without_run_total=0`、`hidden_clarification_total=0`（`/agent/metrics` 实测，见 `metrics_final.json`）——即"未确认字段被错误展示为已确认次数必须为 0"这一硬性目标在 150 个真实回合上保持为 0。

**S1 多人集合 + 上午景点推荐 + 路途时长估算** — ⚠️ PASS（含瑕疵：景点推荐偏弱）（研究耗时约 4 分钟）

| 1 | 高 | 目的地澄清死循环：模型追问城市后，用户回答"上海/就是上海市内"仍反复追问同一问题，无法进入研究 | `interpreter._pending_answer_patch` 只把短答案绑定到 `origins` 槽位，未处理 v4 前置解析产生的 `destination` 阻塞槽位；且 `decision` 的 NEEDS_INPUT 分支复用模型草稿导致承诺语言泄漏 | 已修复 |

| 3 | 中 | 禁止搜索本地重排时，用户口头指定但未入库为候选卡的地点（武康路）被静默丢弃，且明确要求加回仍失败 | recompose 的 `itinerary_draft` 经 `_normalize_itinerary_draft` 按当前 bundle 的 `activities` 标题接地过滤，非候选卡地点被过滤 | 已定位根因，作为发现上报（涉 v3 候选接地逻辑与其独立测试套件，未在本轮改动） |

| 5 | 低-中 | 首轮目的地抽取摩擦："在上海市内"等口语未被可靠映射为目的地，多次首轮进入 needs_input 追问城市（回答"上海"即可继续） | 真实 LLM/确定性抽取未从"上海市内"的表述中提取 target_city_name | 已记录（体验摩擦，非阻断；可在抽取层补一条“X市内/X本地”→目的地的确定性规则） |

### 修复详情

- **缺陷 1**：`copilot/interpreter.py::_pending_answer_patch` 增加 `destination/target_city_name` 槽位的短答案绑定（含"就是上海市内"等口语）；`agent/decision.py` 的 NEEDS_INPUT 分支改为固定运行时措辞，不再复用模型草稿（杜绝无 Run 时的承诺语言，符合 v4 §8.3）。回归：`tests/test_v4_api.py::test_destination_clarify_loop_broken_by_short_answer`。浏览器复验：回答"上海"后 turn 从 needs_input 转 `running`（截图 `S1_03_城市追问循环已修复_回答后转 running.png`）。
- **缺陷 2**：`bff/app.py::ImportBody.kind` 增加 `"manual"`。回归：`tests/test_v4_api.py::test_booking_import_accepts_manual_kind`。浏览器复验：S7 回填成功进入确认版。

### 缺陷 3 建议修复方向（供后续决策，未实施）

recompose 时保留用户在 `itinerary_draft` 中明确点名的地点：允许 recompose 的行程行携带非候选卡的用户命名地点（作为 `user_pinned` 标记），或在接地过滤时把"历史 itinerary_draft 已出现过的标题"纳入已知集合。因该逻辑被 `tests/test_candidate_lifecycle_refactor.py` 等覆盖，改动需连带回归候选生命周期，建议单独立项。

## 八、多轮长程对话覆盖（2026-07-31 补测）

针对"任务复杂多变：想去 A → 又想加 B → 想吃餐厅 → 中途变更/删除"的诉求，专项补充多轮长程覆盖。

### 8.1 自动化用例（`tests/test_v4_multiturn.py`，8 个，离线确定性，均绿）

| 用例 | 覆盖的多轮语义 | 断言 |
|---|---|---|
| 目标跨轮累积 | 想去豫园 → 又加外滩 | 第二轮后 `research_subgoals` = [豫园,外滩]；mode=research_more（续研非重启） |
| 运行中追加 → child run | 父任务未完时追加 | 新 run.parent_run_id = 父 run；父任务不取消 |
| 中途改目的地 → 替换 run | 上海 → 改杭州 | 旧任务 cancel_requested=True、replaces_run_id 置位、新 thread、parent=None |
| 禁搜索保留重排 | 保留豫园、下午加外滩 | recompose；回复含豫园+外滩、"未做外部搜索"、无指针 |
| 删除某项 | 要豫园+外滩 → 不要外滩 | 约束收缩为只剩豫园 |
| 混合轮 | 改预算 + 再加展览 | 约束 budget 更新 且 同时创建研究任务 |
| 长程连续（4 轮） | 豫园→外滩→餐厅→展览 | 会话逐轮累积、Turn 序号 1..4、解释器每轮收到增长的历史、最终四个子目标均在 |
| 运行中纯问答 | 研究在跑时问"外滩要门票吗" | 直接 ANSWERED、不新建 run、在跑任务不受扰 |

### 8.2 浏览器真实长多轮会话（plan 5305，真实 LLM+搜索）

- T1 去豫园 → ✅ 自洽回复（内联时间/地点/门票/证据，拓展出豫园/城障庙/湖心亭/外滩等一日线）。
- T2 追加本帮菜餐厅（继承上下文）→ ✅ 走 research_more；回复自洽（无指针）、尊重预算找到生煎（大壶春）；子目标正确累积为三项。
- T3 变更重排（把豫园/午餐/展览排成一天）→ ❌ **缺陷 4**：重排只剩大壶春+莫兰迪展，明确点名的豫园被丢。
- 结论：**多轮分派与累积（child/替换/续研/子目标）均正确、回复跨轮保持自洽**；但**具体锚点候选的跨轮保留不足**（缺陷 4，与缺陷 3 同源）。
- 截图：`MT_01_追加餐厅_累积正确但锡点丢失.png`、`MT_02_变更重排_显式点名的豫园仍被丢.png`。

### 8.3 缺陷 4 建议修复方向（与缺陷 3 合并立项）

在 research_more 的 reflect/selection 阶段，把"上一轮已显式排入 itinerary、且对应用户 required 子目标"的锚点强制作为 baseline 候选保留；并与缺陷 3 的"用户命名地点可跨轮锤定"一并处理。因涉候选生命周期与其冻结测试套件，建议单独立项、在 plan 模式下设计。
